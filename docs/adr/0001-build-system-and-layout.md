# ADR 0001：构建系统与工程布局

- 状态：已采纳
- 日期：2026-10-06

## 背景

全新仓库（`.reference/` 下是旧版 2048ai 与 KataGo 的检出，只作参考，不参与构建）。
要同时容纳：C++ 规则/搜索/跑谱内核、PyTorch 训练与推理、两者之间的批推理扩展模块。
必须避免旧版与 KataGo 各自的构建痛点：

* 旧版把 CLI 源码 `#include` 进扩展模块的 `.cpp`，于是“改了哪个文件该跑哪个脚本”
  必须写进文档，两份产物还可能不同步；`.pyd` 直接写进源码包目录，`.gitignore` 甚至没覆盖。
* KataGo 的 CMake 为一个可移植单文件二进制服务：2085 行、单目标编入全部测试、
  无 ccache/无 CTest/无 sanitizer，任何改动都要重链整个引擎。

## 决策

1. **CMake 是唯一的构建真相**。Makefile 只负责环境与转发，不重新实现构建逻辑。
2. **一个构建树、四类目标**：静态库 `r2048_core`（零第三方依赖）、CLI `r2048`、
   测试 `r2048_tests`、pybind11 模块（导入名 `r2048_core`，目标名 `r2048_pyext`）。
3. **源码显式列举**，不用 GLOB；选项集中在 `cmake/R2048Options.cmake`。
4. **测试是独立目标**，由 CTest 按套件注册，不编进发行二进制。
5. **扩展模块的输出是顶层模块 `r2048_core`**，位于 `build/pyext/`，靠 `PYTHONPATH` 引入，
   源码树内不出现任何二进制产物。
6. **Python 侧用 uv 管理**，根级 `pyproject.toml`，src 布局，可编辑安装；
   扩展模块不由 PEP517 后端构建（见替代方案）。
7. 构建产物落在 `build/bin`、`build/lib`、`build/pyext` 固定位置。

## 理由

* 静态库 + 多个薄目标解决了旧版最贵的两个问题：源码只有一份（不再靠 `#include .cpp`），
  增量构建只重编受影响的目标。
* 扩展名与包目录解耦（`r2048_core` 而不是 `r2048._core`）：可编辑安装的包与 PYTHONPATH
  上的同名包目录会互相遮蔽，顶层模块名从结构上绕开了这个问题，也让源码树保持干净。
* `make build` 走的是 `cmake --build`，改一行 C++ 只需一次 ninja 增量链接，
  不必经过 Python 打包链路——这是日常最高频的操作，值得单独优化。
* CTest 按套件切分后，单跑某类不变量（例如规则一致性）不需要重编任何东西。

## 替代方案

* **scikit-build-core（PEP517 构建扩展）**：`uv sync` 即得可用扩展，是更“标准”的做法。
  放弃的原因：C++ 迭代被绑到 Python 构建工具链上（改一行 C++ 要走 `uv sync`/重装包），
  而 C++ 是本项目改动最频繁的部分；此外裸 cmake 与 build backend 共用构建树时
  两者的配置参数（安装前缀、构建类型、生成器）容易不一致。
* **`cmake --install` 装进 `.venv`**：省掉一条 PYTHONPATH，但 uv 在同步时会清理
  非它管理的文件，属于已知隐患。PYTHONPATH 由 Makefile 统一注入，代价只有一行。
* **产物直接写进源码包目录（旧版做法）**：零导入配置，代价是源码树里出现二进制、
  CLI 与扩展容易不同步、`.gitignore` 漏网。明确排除。
* **KataGo 式单目标 + 测试编入二进制**：适合“发布单个可执行文件给最终用户”，
  与本项目“本地高频迭代 + 嵌入 Python”的形态相反。

## 验证方式

* `make build` 从零可复现；`make test` 跑通 CTest 五个套件 + pytest。
* `python -m r2048 version` 能同时报出 Python 包与 C++ 内核的版本与构建身份。
* 增量：改一个 `game/*.cpp` 只重编该文件并重链相关目标（ninja 输出可核对）。
