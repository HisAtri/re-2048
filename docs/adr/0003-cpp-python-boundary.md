# ADR 0003：C++/Python 职责边界与两阶段批推理

- 状态：已采纳
- 日期：2026-10-06

> 编码的全局实现位置已由 [ADR 0054](0054-model-owned-input-encoding.md) 订正：仍由 Python 编码，但归属各模型定义内部。

## 背景

神经网络的推理要放在哪一侧，决定了整个工程形状。两条极端路线：

* **KataGo 式全 C++**：搜索与推理都在 C++（cuDNN/cuBLAS 手写后端 + 自定义权重格式），
  Python 只做训练。优点是单进程、无跨语言边界；代价是约十万行后端代码、
  自研权重格式，以及为了格式演进写出的九个 `migrate_*.py`。
* **推理全在 Python**：C++ 只做规则，每次都跨语言取一次价值，等于把语言边界
  放进内循环。

旧版（2048ai）选了折中路线并在同一台机器上实测跑得动：C++ 持规则/搜索/对局/落盘，
Python 只做 NN 前向；边界上是**批**而不是单样本。它的实测数字（随机跑谱
≈144 万样本/秒、MCTS-64 ≈2400 样本/秒）说明这条路线足以支撑研究。

本项目的关键差异是**双头网络**：价值头看 afterstate `u = T(s,a)`，策略头看决策局面 `s`。
搜索展开一个决策节点时，同时需要 1 个决策态的策略结果与最多 4 个 afterstate 的价值结果。

## 决策

1. **C++ 拥有**：规则、编码无关的棋盘状态、搜索树、自对弈对局、训练数据落盘与校验。
   **Python 拥有**：神经网络定义与训练、批推理服务、编排（阶段/断点/注册表）、评测分析。
2. **边界是两阶段批协议**：
   `advance(max_requests)` 返回一批 `(request_id, kind, board)`；
   Python 一次前向；`submit(ids, values, policy_logits)` 回填。
   `kind ∈ {value, policy}`，`values` 是**归一化**价值（分数 / `score_scale`），
   C++ 侧换算回原始分数。
3. **一次决策节点展开 = 1 个策略请求 + 最多 4 个价值请求**，两种请求在同一批里
   由同一次前向算完（两个头都算），因此每次前向覆盖的局面数天然是请求数的 1 倍以上，
   而每个节点又带来 5 个请求。
4. **线上只传原始棋盘**（16 个 u8 指数），永不传编码后的特征：编码只存在于
   `python/src/r2048/nn/encode.py` 一处。
5. **C++ 侧绝不逐样本调用 Python**；反之 Python 侧也只通过 `advance/submit` 驱动引擎。
6. **并行放在“CPU 搜索 ∥ GPU 推理”这条流水线上，而不是 tree 内部**：`advance`/`submit`
   期间释放 GIL，Python 只在自己的线程里做前向；`advance` 内部的多个 lane 目前是
   **顺序推进**的。这是一个实测决定，不是省事：在同一台机器上，管线时间里
   `advance` 只占约 5%（`evaluate` 占 93%），给 lane 推进加线程最多省下 5%，
   却要把一整类并发缺陷引进来（见下文“被实测否定过的做法”）。
7. **每个 lane 允许在途多条模拟**（`in_flight_per_lane`）。这是吞吐的关键：在途只有 1 条时，
   流水线退化成“算一个叶子 → 等一次 GPU 往返 → 再算下一个”，实测批次小到 4 行、
   吞吐 13 样本/秒。允许在途多条后，一次前向覆盖 `lanes × in_flight` 个叶子。
8. **推理缓存**：键为 `(board, kind)`，2 路组相联 + 近似 clock 替换。
   缓存命中意味着这次叶子求值完全不跨语言。缓存把某个等待中的模拟需要的结果挤掉时，
   在没有任何在途请求的情况下会补发请求（否则该 lane 会永久等待——这是实现中
   真实出现过的死锁，必须保留这条自愈路径）。

## 理由

* 双头的两个输入不同，但它们可以放进同一个张量批次：这让“5 个请求一次前向”
  成为自然结果，而不是额外的工程技巧。
* 权重就是 PyTorch checkpoint，**没有自定义权重格式**，因此也没有格式迁移脚本；
  代价是推理必须在 Python 侧（可接受，因为推理本来就要用 PyTorch 的算子）。
* 编码只在 Python 一处：这是最容易两侧悄悄分叉的东西，从结构上排除它比写测试更省事。
* C++ 内并行 + GIL 释放：调用方即使是单线程 Python，也不会出现“CPU 等 GPU”的形态。
  lane 之间完全独立（各自的树与对局），共享的只有缓存与请求队列，都在短临界区内访问。

## 被实测否定过的做法

并行 lane 推进（线程池 + 阶段同步）曾实现并试跑，遇到三类真实故障，最终撤掉：

1. **缓存驱逐导致的活锁**（真正的元凶）：一个决策节点要同时命中“策略 + 最多 4 个
   afterstate 价值”才能展开。早期用“2 路组相联”缓存，几个高频局面撞进同一个 set 后
   互相驱逐，于是同一批请求被无限补发，引擎每秒处理几十万次请求却推进不了任何一步。
   修法有三处，缺一不可：改用容量远大于工作集的开放寻址表；挂起模拟缺的**整组**结果
   一起请求（而不是只补当前缺的那几条）；回填时逐条结果就尝试解析等待它的模拟。
2. **锁序死锁**：engine 的两把锁（缓存、记账）在 pump 与 submit 里的获取顺序相反，
   形成死锁环；现在约定两把锁**永不嵌套**。
3. **线程池的握手缺陷**：用“世代号 + 条件变量广播 + 手工计数”实现“每个 worker 恰好
   参与一次”是错的——漏一次就永久等待，多减一次就让调用方提前返回并访问已析构的
   栈上闭包。用 `std::barrier` 重写后不再有这个问题，但此时第 1 类故障已经证明
   “并发不是瓶颈所在”，于是也不再需要它。

教训：先把吞吐瓶颈测出来再决定要不要并发。这一步如果早点做，上面三类故障都不会被引入。

## 替代方案

* **C++ 内嵌 libtorch**：单进程无边界，但 C++ 构建强耦合 libtorch 的 ABI 与版本，
  编译极慢，且网络结构一变就要重编 C++——与“网络结构在本项目里会频繁改动”直接冲突。
* **C++ 自研 CUDA/cuDNN 后端**：性能上限最高，代价是 KataGo 那一整套复杂度
  （后端抽象、权重格式、内核调优），对 2048 这种小网络收益远小于成本。
* **每条 lane 一个 Python 线程、各自持有一个引擎**（旧版形态）：能达到并行，
  但线程数、GIL 竞争、以及“Python 线程调度参与搜索进度”都成了额外变量；
  把并行下沉到 C++ 后，Python 侧只需要一个循环。
* **一次性把所有 pending 请求交给 Python**（无 `max_requests` 上限）：请求队列无界增长，
  且在目标接近达成时会做大量无用功。上限 + 下一轮再取更简单可控。

## 验证方式

* 端到端链路：`python -m r2048 selfplay --random-init` 能产出通过 `r2048 verify` 结构校验的数据批。
* 统计口径：`engine.stats()` 报告 `requests_issued/requests_submitted`（应相等）、
  `leaf_from_cache / leaf_evaluations`（叶子缓存命中率）、每批平均行数。
* 实测（16 核 WSL2 + 单张直通 GPU，随机初始化模型，sims=64，lanes=32，in_flight=4）：
  见 `docs/BUILD.md` 的性能记录一节；对照是“在途 1 条”时批次 4 行、13 样本/秒。
* 未验证的边界：跨设备（CUDA/CPU）批大小对数值结果的影响尚未量化；
  NN 自对弈因此不承诺“逐字节可复现”，只承诺同配置同设备下一致（见 ADR 0007）。
