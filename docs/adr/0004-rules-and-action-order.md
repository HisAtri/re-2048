# ADR 0004：规则语义与动作顺序契约

- 状态：已采纳
- 日期：2026-10-06

## 背景

规则是整条流水线的地基：规则错一点，所有训练数据都是错的，而且很难从分数上看出来。
同时，动作顺序、棋盘含义这些“跨语言接口”一旦两侧理解不同，错误会非常隐蔽
（策略头的四条输出对不上方向，网络照样能训练，只是学的是错的）。

旧版已经把规则语义与动作顺序固定下来并跑过完整实验，本项目直接沿用，不重新发明。

## 决策

1. **棋盘**：4×4，每格存**指数**（0 = 空，1 = 2，2 = 4，…）。
2. **移动**：每条线上的非零块先压缩，再从左到右贪心合并；**每个块每回合至多合并一次**。
   合并得分是新块的数值（`2^指数`），本次移动的得分是所有合并之和。
3. **生成**：有效移动后，在有空格中均匀选一格，生成 2（90%）或 4（10%）。
   **无效移动不生成新块**，也不改变局面。
4. **终局**：没有任何合法方向。达到 2048 后继续游戏（研究 4096 以上的大块）。
5. **动作顺序冻结为 `UP=0, RIGHT=1, DOWN=2, LEFT=3`**。这是跨语言硬契约：
   策略头四条输出、数据记录里的访问数顺序、推理缓存键都按它排列。
6. **价值语义**（沿用旧版定义）：
   记 `s` 为决策局面，`a` 为方向，`u = T(s,a)` 为 afterstate（移动后、生成块前），
   `r(s,a)` 为本次合并得分，`s'` 为从 `u` 生成随机块后的局面。
   * `A(u)`：从 afterstate 出发的期望新增得分，**不含**产生 `u` 的那次合并。
   * `Q(s,a) = r(s,a) + A(T(s,a))`。
   * `V(s)`：从决策局面出发、按指定策略继续的期望新增得分；终局 `V = 0`。
   训练标签必须采用同一种策略语义，不允许混用。
7. **分数尺度** `score_scale = 1024`：网络输出以“分数 / 1024”为量纲，
   C++ 搜索内部一律用原始分数，只在跨语言边界上换算。
8. **C++ 侧是规则的唯一实现**；Python 侧只有一份**仅供测试**的参考实现
   （`python/src/r2048/reference/rules_reference.py`），它不参与任何生产路径。

## 理由

* 沿用旧版语义的最大价值是可比性：实验数字、ADRA 结论、失败档案都还能对上。
* 每个块每回合至多合并一次是标准 2048 规则，也是旧版实现与全部已有数据的口径。
* action order 必须显式冻结并测试，因为它是 C++/Python 之间**唯一没有编译器保护**的契约。
* 规则只在 C++ 实现一次，Python 参考实现只做判据：两份生产实现必然分叉。

## 替代方案

* **重新设计棋盘表示或动作顺序**（例如按“上右下左”的直觉顺序编号）：
  收益为零，风险是把旧版的全部结论与数据作废。
* **把规则也用 Python 实现一份供 C++ 调用**：性能灾难，且引入第二份生产语义。
* **在 C++ 里限制指数上限**（例如 nibble 表示只能到 2^15）：会与研究大块的目标冲突，
  见 ADR 0005。

## 验证方式

* C++ 侧：`r2048_tests rules` 覆盖手算用例、单行穷举（指数 0..4 的全部 5^4 组合，
  放在每一行与每一列）、20 万个随机棋盘（查表实现 vs 标量参考实现逐格逐分比对）、
  生成块分布（90/10、空格均匀）、种子确定性。
* 跨语言：`python/tests/test_rules_conformance.py` 用 Python 参考实现生成期望向量
  （边界局面 + 2 万随机棋盘），交给 C++ 测试二进制逐条比对。
  两侧都不共享代码，因此这是真正独立的判据。
* 两者均在 `make test` 中执行。
