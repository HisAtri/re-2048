# ADR 0007：训练数据格式与来源校验

- 状态：已采纳
- 日期：2026-10-06

## 背景

自对弈数据是这条流水线里唯一“不可重建地昂贵”的东西：几十万到上千万条样本、
每一条都对应一次真实搜索。数据一旦写坏、写混、或者被另一套规则语义解释，
后果会一路传导到训练结果，而且很难在事后发现。

旧版把 value 样本与 policy 样本分成两个文件流，代价是每个批次都要校验
“两条流按局号/步号对齐”。它确实靠这套校验抓住了问题，但也为此付出了持续的复杂度。

## 决策

1. **一条记录 = 一次真实决策**，固定 80 字节，小端，显式序列化（不依赖编译器对
   结构体的填充）。字段与偏移见 `cpp/dataio/sample.h`：决策局面、afterstate、
   实际动作、合法掩码、步号、局号、模拟次数、立即得分、MC 回报标签、四方向根访问数，
   末尾留 16 字节保留位。
2. **一个批次 = 一个目录**：`manifest.json` + `shards/shard-NNNNNN.bin`。
   分片按样本数切分（默认 10 万条/片），最后一个分片可以不满。
3. **`manifest.json` 是提交标记**：它最后写入，且记录每个分片的 sha256、条数、
   覆盖的局号范围，以及批次的来源：批次号、策略、模拟次数、温度步数、种子、
   模型标识、记录格式/规则/协议版本、构建身份（git 描述 + 编译器 + 标志哈希）、
   以及当次命令行的原始参数。
4. **写入按局号顺序**，且样本数**恰好**等于目标条数（最后一个不完整的局被截断）。
   因此数据文件逐字节只由 `(种子, 参数, 目标条数)` 决定，与线程数、lane 数、
   执行顺序都无关。
5. **`verify` 子命令**做两级校验：
   * 结构与摘要：清单与分片一致、每片 sha256、记录内局号单调、分片容量与局号覆盖；
   * 重放：用清单里的参数重新生成整批数据并逐分片比对哈希——**故意用与生成时不同的
     线程数**，因此它同时证明了“数据布局与并行度无关”。
6. **版本不匹配直接失败**：清单里的记录格式版本或规则版本与当前内核不一致时，
   读取即报错，不做兼容猜测。
7. **NN 自对弈的可复现性边界**：浮点批大小会改变归约顺序，因此用 NN 跑谱时，
   “逐字节可复现”以“模型、设备、批处理配置都相同”为前提；纯 C++ 跑谱（random/mcts）
   则无条件可复现。

## 理由

* 一条记录承载一次决策的全部信息，使“策略目标与价值目标来自同一次搜索”成为结构性事实，
  而不是靠两套文件流的对齐校验来保证。
* 固定 80 字节 + 保留位：加字段时不必改记录长度，也就不必写迁移脚本（KataGo 因为自研
  权重格式付出了多个 `migrate_*.py` 的代价，这个坑值得避开）。
* 来源信息必须写进数据本身而不是留在命令行历史里：一批数据能不能和另一批混着训练、
  能不能解释某个指标变化，全靠这些字段。
* `verify` 的重放校验是本项目对“数据可信”的核心承诺：任何一批数据都能被独立重放并
  逐字节比对。它抓住过真实的记账错误（局计数把被丢弃的局算进去、写入侧的局号空洞）。

## 替代方案

* **沿用旧版的两条文件流**：需要持续维护对齐校验，且新增头/字段时要同时改两处；
  合并成一条记录后这些复杂度直接消失。
* **npz/parquet/自定义容器**：读取端更灵活，但要引入第三方依赖（C++ 侧零依赖是硬约束），
  且固定宽度记录对顺序读与 mmap 已经足够高效。
* **按局保存文件**（KataGo 的 tdata 形态）：小文件数量爆炸，且对“按样本数切分”的
  并行生成不友好。

## 验证方式

* `r2048_tests dataio`：样本编解码往返、回报标签口径（`标签_t = 得分_{t+1} + 标签_{t+1}`、
  末步为 0）、清单 JSON 往返与版本不匹配报错、不同线程数产出逐字节相同、
  篡改分片或清单必须被发现、拒绝覆盖已有数据批。
* `r2048 verify --data <批>`：含重放校验的完整检查（生成时 16 线程、重放时 3 线程，
  哈希必须一致——这条在实测中通过）。
* `python/tests/test_selfplay.py`：NN 自对弈产出的批次通过 C++ 侧结构校验；
  相同配置两次运行分片哈希相同。
