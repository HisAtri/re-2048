# ADR 0008：输出目录布局与默认命名

- 状态：已采纳
- 日期：2026-10-06

## 背景

跑谱数据、模型、评测结果都需要一个稳定的落点；同时仓库本身位于 9p 挂载
（`/mnt/e`），大规模写盘与内存映射读取在那里明显更慢。旧版已经引入了
“输出根可由环境变量重定位”的做法，本版沿用并明确边界。

## 决策

1. **输出根**：`R2048_OUTPUT_DIR`（未设置时用当前目录下的 `output/`）。
   C++ 与 Python 读同一个环境变量，因此不需要互相传路径。
   两边各有一份三行实现（`cpp/core/paths.h`、`python/src/r2048/paths.py`），
   刻意不为了“传一个路径”而在跨语言边界上加参数。
2. **布局**：`data/<批次号>/`（跑谱批）、`runs/<运行号>/`（训练/评测运行）、
   `models/<模型号>/`（发布产物）、`eval/`（逐局评测记录）、`benchmarks/`（机器画像）。
3. **默认命名**：
   * 数据批：`<策略>[-s<模拟次数>]-<日期>-<时刻>`，例如 `mcts-s64-20261006-1330`；
   * 评测文件：`<策略>[-s<模拟次数>]-<日期>-<时刻>.jsonl`；
   * 模型号由训练阶段使用“架构 + 模拟次数 + 数据批 + 递增序号”的形式（后续 ADR 记录）。
   默认名只用于**人读**；所有产物内部都写自己的身份字段（模型号/批次号），
   不依赖目录名传递语义。
4. **命令行输出分工**：stdout 只放可被脚本消费的结果（`generate` 打印 manifest 路径、
   `evaluate`/`verify` 打印一行 JSON 摘要），进度与统计走 stderr。
5. **拒绝覆盖**：数据批目录已存在且非空时直接失败（跑谱批按“整批要么完整、要么重来”管理）。
6. 构建目录和虚拟环境默认放在仓库外的本地文件系统（见 ADR 0002）；输出根默认是
   仓库根目录下的 `output/`，可由 `R2048_OUTPUT_DIR` 覆盖（后续调整见 ADR 0046）。

## 理由

* 路径解析走环境变量而不是参数：`r2048 generate` 与 `python -m r2048 selfplay`
  需要看到同一份数据，若各自维护路径参数，两边迟早不一致。
* stdout 只放结果、stderr 放进度：让 `r2048 generate ... | tail -1` 之类的用法
  不会把进度行混进数据里——这条在写脚本时非常值钱。
* “人读的目录名”与“机器读的身份字段”分离：目录可以被重命名或移动，
  产物自身的语义不受影响。

## 替代方案

* **把路径作为参数在两侧显式传递**：调用方（Makefile、脚本）需要记住并在每处重复，
  且容易一边改了另一边没改。
* **输出根随构建目录放在仓库外**：能减少 9p 写盘，但数据与模型散落在项目之外，
  不利于按项目查看和管理；本项目接受输出数据的写盘开销，构建仍留在仓库外。
* **数据与模型分开放到两个根**：多一个必须记住的约定，收益不明。

## 验证方式

* `python -m r2048 env` 打印解析后的输出根；`r2048 generate` 默认写到
  `$R2048_OUTPUT_DIR/data/<批次号>`。
* `r2048_tests dataio` 覆盖“拒绝覆盖已有数据批”。
* Makefile 里三个目录都可用环境变量覆盖（`BUILD`、`OUTPUT`、`VENV`），
  并在 `make env-check` 时打印实际取值。
