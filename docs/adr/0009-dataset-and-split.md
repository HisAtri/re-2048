# ADR 0009：训练数据的读取与划分口径

- 状态：已采纳
- 日期：2026-10-06

## 背景

数据格式的权威定义在 C++ 侧（`cpp/dataio/sample.h`，80 字节定宽记录）。Python 侧要读它，
于是存在“同一份格式、两处解释”的风险：偏移算错不会报错，只会安静地喂进一批看着像棋盘的垃圾。
同时，训练/验证怎么切分直接决定验证指标是否可信。

## 决策

1. **用结构化 dtype 对 mmap 做零拷贝视图**（`python/src/r2048/data/shards.py` 的 `RECORD_DTYPE`），
   偏移与 C++ 注释逐项对应，并在模块导入时断言 `itemsize == 80`。
   **不做逐条 Python 解码**：千万级样本上那会立刻成为管线瓶颈。
2. **分片用 mmap 打开、不整体读入内存**：训练按批随机取样，把整批读进内存会吃掉数 GB；
   mmap 让内核按需换页，多个 worker 也能共享同一份只读映射。
3. **按整局划分训练/验证**，划分方式用 splitmix64 混合 `(局号, seed)` 后取阈值，
   因此**与样本顺序无关**：打乱数据或追加新批次不会改变已有局的归属。
   种子必须以乘法折进状态，不能简单加常数——加常数只让哈希整体平移一个小量，
   在局数少时选出的验证集可能与不换种子时完全相同（这个缺陷被测试抓到过）。
4. **标签口径固定**（与 ADR 0004 的价值语义一致）：
   * 价值目标 = `mc_return / score_scale`，即该 afterstate 之后的实际新增得分，**不含**
     产生它的那次合并得分；
   * 策略目标 = `visits / simulations`，按每条记录自己的模拟次数归一化（同批数据可能来自
     不同搜索预算）；
   * `visits` 全 0 的记录（随机策略或贪心模式产出的）**必须从策略损失中排除**，
     不能当成“均匀分布”来训练。
5. **跨语言契约用 C++ 当判据来测**：逐条样本核对 `afterstate`、`move_score`、`legal_mask`
   与 C++ 规则一致；并按局重算 `标签_t = 得分_{t+1} + 标签_{t+1}`、末步标签为 0。

## 理由

* 偏移表错位的后果是“训练照跑、指标照降、模型全错”，只有用独立判据（C++ 规则）能发现。
* 验证指标的用途是挑 checkpoint 与排查，不是验收（验收见 ADR 0011）。而按样本随机切分会让
  同一局的相邻局面同时出现在两侧，验证指标虚高、失去排查价值——旧版明确记录过这个坑。
* 按局哈希划分而不是“取后 5% 的局”，是为了让数据增长时划分保持稳定：课程训练会把多个批次的
  数据混在一起，划分一变，历史指标就不可比了。

## 替代方案

* **用 PyTorch `DataLoader` + 逐样本 `Dataset.__getitem__`**：每条样本一次 Python 调用与一次
  张量构造，在本项目的样本规模上会直接把 GPU 喂不饱。当前实现完全向量化（批量结构化视图 +
  批量转张量），实测解码约 1.1 ms / 8192 条。若将来出现多 worker 需求，按分片切索引即可，
  不需要改数据格式。
* **存储为 npz/parquet**：读取端更灵活，但要引入 C++ 侧依赖，且固定宽度记录已足够高效。
* **把编码后的特征落盘**（而不是原始棋盘）：文件体积翻 25 倍，且把编码写进了数据格式，
  编码一改就要重跑全部数据。

## 验证方式

* `python/tests/test_data_and_training.py`：
  * 记录布局：逐条用 `r2048_core.apply_move` / `legal_mask` 复核 afterstate、得分、掩码；
  * 标签口径：按局重算递推关系与末步为 0；
  * 划分：同 seed 可复现、不同 seed 必须不同、同一局不得跨两侧；
  * 批次流：随机策略数据的策略目标必须为 0，且此时 `policy_loss` 返回 `None`。
* 实测：300 万条数据（100 万样本 × 3 个批次）上，读局号列约 0.08 s，解码约 1.1 ms/批。
