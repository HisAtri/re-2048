# ADR 0017：批组成不是浮点问题——在途模拟的调度依赖与它的强度代价

- 状态：已采纳
- 日期：2026-10-06

## 背景

ADR 0016 决策 5 记录了一个实测：NN 路径下只改 `lanes` 就得到完全不同的轨迹，
并把它归因于**浮点**——"批大小改变前向结果，临界局面的选招被这点差异翻转"。

这个归因在写完之后被自己的验证否掉了。要否掉它并不需要新理论，只需要问一句：
**若通道是浮点，那噪声小四个数量级的那一侧应该几乎不受影响。** 于是做了四个对照，
结论是通道根本不在算子层，而在**在途模拟（in-flight）把搜索切分成什么样**。
这件事的后果比 ADR 0016 决策 5 大得多，因此单独成条，并订正那条的归因。

## 决策


1. **订正机制：`lanes` 等批组成改变结果的通道是在途模拟的调度切分，不是浮点。**
   四条证据，前三条用来否定浮点，第四条给出正面的机制定位：

   * **批内位置无影响。** 同一局面重复 320 份放进一个批：value 逐位相同（极差 0），
     logits 极差 8.2e-8。把整批循环移位后让同一行回到位置 0，logits 差**恰好 0**。
     所以"批组成"里真正起作用的维度只有批大小，没有行序。
   * **浮点确实依赖批大小，但量级小、且是阶跃。** 在 50000 个真实自对弈局面上取最大差
     （基准 = 批 5）：

     | 批大小 | 8 | 16 | 32 | 64 | 128 | **320** | 1024 |
     |---|---:|---:|---:|---:|---:|---:|---:|
     | \|Δvalue\| | 0 | 0 | 4.8e-7 | 4.8e-7 | 4.8e-7 | **5.8e-4** | 3.9e-6 |

     320 那一格跳三个数量级又回落，是 cuDNN 按批大小切换内核的特征；CPU 上同样对照只有
     **1.5e-8**。`cudnn.benchmark / deterministic`、`torch.use_deterministic_algorithms`
     三个开关都**压不掉**它（只改 `float32_matmul_precision` 会改变数值，说明来源确实是
     归约顺序），因为这三者只收缩算法集合，而算法选择本身仍随批大小变。
   * **否定浮点解释的决定性对照**：同一 seed、同一参数、只改 `lanes` 8→16，
     **GPU 上 1/16 逐局一致，CPU 上也是 1/16**。CPU 的批大小浮点噪声比 GPU 小四个数量级，
     若通道是浮点，CPU 该接近全一致。它没有。
   * **正面定位。** `in_flight=1`（每个 lane 一次只跑一条模拟，彻底结算后再开下一条）
     时，`lanes` 8→16 在 **GPU 与 CPU 上都 16/16 逐局一致**；`in_flight=4` 时两边都是 1/16。
     再把 `lanes` 固定成 8、只改共享推理缓存的容量：

     | | 缓存 131072 vs 1048576 | 缓存 131072 vs 1024 |
     |---|---:|---:|
     | `in_flight=4` | 3/16 | **0/16** |
     | `in_flight=1` | **16/16** | **16/16**（三种容量均分都恰好 13102.0） |

     机制如下。一条模拟在 `start_simulation` 里沿路径把 `edge_visits[action]` 自增，
    `edge_q_sum` 却要等回填才更新；若该叶子需要神经网络，这条模拟挂进 `pending`
    而**不回填**。于是同时在途的模拟看到的是"半计价"的树：在途子节点的 Q 被低估、
    而探索项用的 `node.visits` 也滞后。**一条模拟会不会挂起，取决于共享推理缓存里是否
    已有该 (board, kind)**——命中就在 `start_simulation` 内直接完成，根本不进在途。
    缓存跨 lane 共享、命中与淘汰取决于全局工作集，于是 `lanes` / `in_flight` /
    `cache_entries` 共同决定了每个决策步的（选择 → 展开 → 回填）序列。

     放大到整局：根节点取的是**整数**访问数的 argmax，顶层两个方向的访问数一旦被这点
     差异换序选招就翻转；而真实对局的随机块来自
     `derive_seed(seed, kSaltEnvironment, episode, step + 1, 0)`，按 (局号, 步号) 派生、
     与轨迹无关，所以**翻转一步 = 同一串随机数落到另一个棋盘 = 余下整局分叉**。
     这正是"每步翻转概率极小"仍能让 16 局里 15 局全不同的原因。

2. **协议变量再扩四项。** 在 ADR 0016 决策 7 的清单上追加
   `in_flight_per_lane`、`cache_entries`、`max_batch`、`device`：
   * `cache_entries` 此前只写在跑谱产物的 manifest `params` 里，从没被当成评测协议；
     上表已证明它单独就能改变逐局结果。
   * `device` 此前没进过任何清单。同一 seed、同一参数、`s32 / lanes 8 / in_flight 4`，
     GPU 与 CPU **只有 2/16 局一致**（均分 8904 vs 8194）。评分因此是**设备相关**的。
   * `in_flight_per_lane` 与 `max_batch`：前者已由本 ADR 直接证明；后者同时改变前向批大小
     （数值通道）与泵循环的截断（调度通道），两条通道都在，所以必须进协议。
   仍在协议外：`eval_seed`、`games`、纯 C++ 线的 `workers`（无浮点、无在途，3 与 16 线程逐字节一致）。
   **已实施**（[ADR 0018](0018-protocol-variable-registry.md)）：清单落到 `r2048.protocol`，
   逐局记录平铺声明这 13 项，评分侧按同一份清单校验并哈希；缺字段拒收，
   `null` 表示“该策略没有这个变量”。纯 C++ 线因此只声明
   `track / rules_version / protocol_version / simulations / temperature_moves`，
   其余为 `null`，而不是给它们填 0。

3. **在途流水线有实质的强度代价，且不是记账损失。**
   `s32`、`lanes 8`、`seed 20262053`、64 局：

   | | 均分 | 中位 | 到 2048 的局 | 每步有效模拟 |
   |---|---:|---:|---:|---:|
   | `in_flight=1` | **12522** | 12162 | **9.4%** | 32.00（恰好 = 声明值） |
   | `in_flight=4` | 8923 | 7136 | **0.0%** | 32.00（恰好 = 声明值） |

   有效模拟数是读跑谱产物里根访问数之和 + 1（ADR 0015 的口径），两边都是 32、不足声明的
   比例为 0.0%。所以这不是"在途吃掉了模拟预算"，而是**同样 32 次模拟被用得更差**：
   在途的那几条选择看的是半计价的树。

   结论：`in_flight` 不是纯吞吐旋钮，它是**吞吐换强度**的旋钮，而这个交换率此前从未测量。
   既有默认值（`EngineConfig::in_flight_per_lane = 8`、selfplay 默认 8）是在未测量的情况下
   选定的。**本 ADR 只记录实测与机制，不改默认值、不动搜索实现**：
   是否给在途模拟补上真正的 virtual loss（把在途也算进 `node.visits` 与 Q 的分母，
   现在是半算）、以及自对弈与评测分别该用哪个 `in_flight`，都需要单独一条决定。


4. **跨设备：逐局可复现不可得；聚合（评分）在 400 局精度下测不出偏移。**
   这条是决策 1 的直接后果追问，结论分两半，不要混起来读：

   * **逐局不可得，而且不是修调度能拿到的。** 同一 seed、同一参数、只换 `device`：
     `in_flight=4` 是 2/16 一致，**`in_flight=1`（调度通道已被消掉）也只有 3/16**
     ——而同设备内改 `lanes` 在 `in_flight=1` 下是 16/16。所以残留的跨设备分叉全部来自
     数值层。数值层单独量：同一批 20000 个真实局面，cuda 与 cpu 的 `|Δvalue|` 最大
     **3.6e-5**、`|Δlogits|` 最大 1.7e-4，而且**先验 argmax 一次都没翻**（翻转率 0.000%）。
     注意这个数值差比同设备内改批大小的还小（后者 5.8e-4）。也就是说：
     **搜索是一个增益极高的混沌放大器——低于"能翻转 argmax"门槛（1e-5 级）的扰动，
     照样让 13/16 局分叉。** 因此不要指望把后端对齐到某个精度就能跨设备复现。

   * **聚合量上没有测出偏移。** 同一 seed、同一参数、`s32 / lanes 8 / in_flight 4`、400 局：

     | 设备 | L（对数均值） | σ | 均分 | 中位 | 平均步数 | 到 2048 |
     |---|---:|---:|---:|---:|---:|---:|
     | cuda | 12.9256 | 0.853 | 9001 | 7112 | 561 | 0.5% |
     | cpu | 12.9202 | 0.823 | 8923 | 7100 | 559 | 1.0% |

     `ΔL = +0.0053`，两侧独立 1.96σ 合并 `±0.1161` → **区间含 0（不显著）**，
     折算 **+1.2 分（95% CI ±26.7）**。逐局 `log2(得分+1)` 的相关系数只有 **r = +0.098**、
     原始得分完全相同的只有 **3/400** 局、**28/400** 局的得分差超过 4 倍。

   * 合起来的读法是：**跨设备的分叉在统计上是"重新抽签"，不是系统性偏移**
     （点估计 1 分、中位 7112 vs 7100、步数 561 vs 559）。**但不能据此宣称设备中性**：
     ±26.7 分的区间与我们据以决策的最小效应（曲线两次翻倍之间最小的 +20.8 分、
     `lanes` 位移 +20.1 分）同阶。要把设备位移证到 ±10 分，需要每设备约
     `400 × (26.7/10)² ≈ 2850` 局。
   * 顺带再次证实配对无用：配对区间 ±25.4 是全样本独立区间 ±26.7 的 **0.95 倍**，
     与 ADR 0016 的结论一致——同 seed 只共享生成块随机流，轨迹分叉后得分不相关。

   * **因此口径定成**：`device` 进协议指纹（决策 2），评分池不混设备；跨设备只做**聚合**
     比较，且必须报出设备位移与其区间；逐局/逐位复现不作为目标。
     若将来确实需要压低这个放大增益，方向是在搜索的**离散决策处加显式容差**
     （整数访问数 argmax 与 PUCT 近似并列的打破规则），而不是去对齐卷积后端——
     但那是另一条决定，本条不实施。


## 理由

* **归因错了比没有归因更贵。** ADR 0016 决策 5 用浮点解释批组成，下一个读到它的人会把
  修复方向定成"锁 dtype、上确定性算子"，而真正该动的是在途模拟的记账。本条的 CPU/GPU
  对照就是为了把这条归因钉死，避免它继续以"已记录"的身份流传。
* **判别器要选能把维度消掉的那个。** 想知道"是结构还是数值"，再测一个 `lanes` 只会得到
  又一个 1/16；`in_flight=1` 把调度这一维彻底消掉，于是能把两个通道分开。
  同理，想定位到缓存这一层，用 `max_batch` 不行——它同时改前向批大小与泵循环截断，
  两个通道混在一起；只改 `cache_entries` 则只动"是否挂起"这一条。
* **强度代价必须单独记，因为它推翻的是引擎里最有道理的一条性能设计。**
  `in_flight > 1` 是 ADR 0003 为了批大小（`lanes × in_flight × 5` 行）而引入的，
  理由充分且实测有效；但它的代价从没被测过。现在知道代价是均分 12522 → 8923、
  到 2048 的局 9.4% → 0.0%。不写下来，下一次调吞吐的人会以为这是免费的。

## 替代方案

* **靠 `torch.use_deterministic_algorithms` / `cudnn.deterministic` 消掉差异**：三个开关都试过，
  差异分毫不动；而且按本条结论本来就压不住——通道在调度层，不在算子层。
* **把 `lanes / in_flight / cache_entries` 固定成一个文档约定**：ADR 0016 决策 5 已否过这条，
  约定会被新脚本绕过。必须让它在结构上进不了同一条评分线。
* **把评测统一到 `in_flight=1` 换取复现性**：代价是批变小、GPU 空转，与 AGENTS.md
  "不得让 CPU/GPU 核心大部分时间在等待"直接冲突。正确顺序是先把协议变量写全
  （决策 2），强度代价另开一条决定。
* **把差异当作"随机性"接受、只报区间**：不行。它不是抽样噪声——同参数重复跑 16/16 一致，
  说明给定配置是确定的；它是**配置**依赖，所以必须进协议而不是进误差棒。
* **把卷积后端对齐到同一套实现（或改用 float64 推理）以求跨设备复现**：方向错。
  跨设备的数值差只有 `|Δvalue|` 3.6e-5，比同设备内改批大小的 5.8e-4 还小，却已经
  足够让 13/16 局分叉（决策 4）——放大器在搜索的**离散决策**处，不在数值精度上。
  压精度是治标，而且 float64 推理要付掉这份吞吐。真要压低增益就在离散决策处加显式容差
  （决策 4 末段），那是另一条决定。
* **跨设备只跑少量局 + 配对检验提高功效**：实测配对无效（配对区间是独立区间的 0.95 倍，
  逐局 r = +0.098）。要判设备位移只能加大 n（决策 4 给了 n ≈ 2850 的估算）。

## 验证方式

* 批内位置与批大小：`/tmp/batch_numerics.py`、`/tmp/batch_numerics2.py`
  （真实局面取 `$R2048_OUTPUT_DIR/data/nn-s64-20261006-181429` 的 `decision` 列，
  50000 条；模型 `$R2048_OUTPUT_DIR/runs/c2-policy-head/model.pt`）。
* 三个后端开关：`/tmp/batch_numerics.py` 的测试 4。
* 设备对照与 `in_flight` 判别器：`/tmp/batch_probe2.sh`、`/tmp/batch_probe3.sh`，
  逐局记录在 `$R2048_OUTPUT_DIR/eval/batchprobe2/`、`eval/batchprobe3/`
  （命令行：`python -m r2048 eval --checkpoint ... --track nn_mcts --simulations 32
  --games 16 --seed 20262053 --c-puct 1.5 --lanes {8,16} --in-flight {1,4}
  --device {cuda,cpu} --jsonl <路径>`）。注意 `lanes` 会被 `min(lanes, games)` 夹住，
  `games` 必须大于待测的 `lanes`——第一版探针用 `games=8` 比 `lanes 8/16`，
  两臂都被夹成 8，得到的"16/16 一致"是无效对照。
* 缓存容量通道：`/tmp/batch_probe4.sh`，记录在 `eval/batchprobe4/`
  （固定 `--lanes 8`，`--cache-entries {131072,1048576,1024}`）。
* 强度代价与有效模拟数：`/tmp/batch_probe5.sh`，记录在 `eval/batchprobe5/`
  与 `data/batchprobe-inflight/`（64 局；有效模拟数读产物的 `visits` 和 `simulations` 列）。
* 跨设备两层之差：
  * 数值层（不经引擎）：`/tmp/device_numerics.py`——同一批 20000 个真实局面在 cuda 与 cpu
    上各前向一次，比 `value / logits` 与先验 argmax 翻转率。
  * 调度通道去掉后的跨设备分叉：`/tmp/device_probe2.sh`，记录在 `eval/device-probe/`
    （16 局，`--in-flight {1,4}` × `--device {cuda,cpu}`）。
  * 聚合位移与 CI：`/tmp/device_probe.sh`，记录在 `eval/device/`
    （400 局 × 2 设备，`s32 / lanes 8 / in_flight 4 / seed 20262053`）；`ΔL` 与区间按
    `r2048.workflows.rating` 的两样本独立口径算，逐局相关系数用同 seed 的局号对齐后求。
* **尚未验证**：① 强度代价的机制归因——"半计价的树"是解释，但把 `node.visits` 的滞后
  与 `edge_q_sum` 的滞后分别消掉各能追回多少分，没测；② `max_batch` 的独立效应只做了
  存在性观察，没有量级；③ 缓存容量 131072 vs 1048576 是 3/16 而 vs 1024 是 0/16，
  这个非单调本身没解释；④ 跨设备位移**只有 1 个 seed**，+1.2 ± 26.7 分不足以判定设备中性
  （要 ±10 分需每设备约 2850 局），也未测第二块 GPU 或另一种 CPU 后端。
