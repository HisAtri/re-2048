# ADR 0018：协议变量收口——清单、归属与拒绝兜底

- 状态：已采纳
- 日期：2026-10-06

## 背景

ADR 0016 决策 5/6 与 ADR 0017 决策 2 列了一份协议变量清单，并说明了两处必须修的口径：
批组成（`lanes / in_flight / max_batch / cache_entries / device`）要进协议指纹，
`eval_seed` 要出协议指纹。但清单本身当时只是文档，代码里的事实是：

* **定义散在三处**，互不知情：`rating.normalize_row` 里硬编码的 dict、
  `evaluate.py` 写出的逐局记录、`cpp/program/evaluate.cpp` 写出的逐局记录。
  写出方连 `rules_version` 都不写，`c_puct` 与批组成根本没出现在任何一条记录里。
* **读者用默认值兜底**：`row.get("c_puct", 1.5)`、`row.get("rules_version", 1)`、
  `row.get("seed", 0)`。于是一次真正用 `c_puct=2.5` 跑的评测，因为没记录该字段，
  被当成 1.5 写进哈希——**两个不同的协议在评分线上静默合并**。
* **`track` 靠猜**：C++ 评测只写 `policy ∈ {random, mcts}`，评分侧用
  `row.get("policy") == "mcts"` 反推评分线。猜错一次，纯 MCTS 的基准锚点就从搜索线上挪走。
* **`eval_seed` 在协议里**，于是同一个模型在两个 seed 上的评测被劈成两条永不合并的线，
  与"池子随数据增长而变准"（ADR 0012）直接冲突。

这些错误的共同点是**不报错**：它们只给出一个无意义的数字。所以这一条的核心不是
"多记几个字段"，而是把协议的归属变成结构性的。

## 决策

1. **协议字段清单是唯一事实来源**：新增 `python/src/r2048/protocol.py`，
   `PROTOCOL_FIELDS`（字段 → 归一化类型）是唯一清单，哈希、校验、字段名都从它派生。
   评测写出方（`evaluate.py`）用**同一个** `build_protocol` 校验自己的产物，
   所以写出方没有第二份清单可以漂移。

   入清单的判据是两条，都来自实测（ADR 0017）：改变它会改变逐局结果，
   且它不能被当成抽样误差吸收（同参数重复跑逐局一致 ⇒ 差异是**配置**依赖，不是噪声）。

2. **缺字段直接报错，`null` 表示"该策略没有这个变量"。** 两者是不同的事：

   | 策略 | simulations | c_puct / temperature / temperature_moves | lanes / in_flight / max_batch / cache_entries | device | inference_precision |
   |---|---|---|---|---|---|
   | `random` | null | null | null | null | null |
   | `mcts`（纯 rollout） | 模拟数 | null（rollout 用自己的探索常数） | null | null | null |
   | `nn_value` / `nn_policy` | null（没有搜索） | null | 实测生效值 | 实测生效值 | `float32` |
   | `nn_mcts` | 模拟数 | 实测生效值 | 实测生效值 | 实测生效值 | `float32` |

   旧实现在阅读时把纯网络 track 的 `simulations` 强行改写成 0——那是把"没有这个变量"
   说成"这个变量的值是 0"，同样是伪造事实。

3. **`eval_seed` 移出协议**，它的位置是评分池的去重键 `game_key`
   （协议是"怎么测的"，seed 是"测了哪几局"）。`games`、纯 C++ 线的 `workers`
   同样不属于协议，理由见决策 5。

4. **记录实测生效值，不是请求值**：`lanes` 会被 `min(lanes, games)` 夹住、
   `device` 会因 cuda 不可用回退到 cpu。记请求值等于让协议与事实不符，
   而协议的全部价值就在于它属实。

5. **`protocol_version` 承担"没有单独入口的实现常量"。** ADR 0016 决策 4 的缺口 C
   （纯 rollout 的探索常数 `RolloutMctsConfig::exploration`、rollout 策略本身、
   批调度的形式）没有配置项，也没有别的地方可记。它们改变逐局结果，
   因此**改动它们必须抬高 `kProtocolVersion`**，否则评分线会跨语义合并。
   这条把"某天有人调了 rollout 的探索常数"从一个不可归因的改动变成一次版本号变更。

   相应地把 `build_id` **排除**在协议之外：每次重建都换哈希会造成大量无谓的假分裂，
   而真正的语义变更由人来抬 `protocol_version`。数据侧的 `build_id` 仍然照记
   （ADR 0007），那里关心的是"这份文件是谁产出的"，粒度不同。

6. **锚点文件升到 v2**：记录锚点自身的协议本体（v1 只有哈希，读不懂这把尺子是什么）。
   载入旧版本直接失败而不是降级使用。同时要求锚点的所有记录协议一致——
   一个锚点混了两个协议，等于一把尺子有两个刻度。

7. **评分输出带上"与锚点不同的字段"**：`compute_ratings` 每组返回
   `protocol` 与 `differs_from_anchor`。分组不是判"能不能比"，而是判"比的是同一件事"
   ——曲线上的每个模拟数都是不同的协议，它们都放在同一个锚点的尺子上，
   而这条线是在什么测量条件下得到的，必须是可读的事实而不是两个哈希是否相等。

8. **放弃旧评分池。** 协议收口之前的逐局记录无法补齐字段（不写迁移工具：
   猜出来的字段就是伪造的协议身份）。基线锚点按新格式重跑；
   `eval/pool*.jsonl` 与 v1 锚点文件留作前协议存档。

## 理由

* **静默合并在评分里是最贵的错误**：它不报错，只给出一个没有意义的数字，
  而且会随时间被后人当成事实引用。所以这里选择了"宁可不给分"——
  缺字段拒收、锚点不唯一拒绝、旧格式锚点拒绝。
* **清单只有一份才不会漂移**。三处各写一遍的代价在 ADR 0016 的测量里已经付过一次：
  文档列了 9 个变量，代码里只有 2 个。
* **`null` 与"缺字段"必须分开**，否则只有两种选择：给一个假的默认值（静默合并），
  或者把"策略没有这个变量"也当成缺字段（纯 rollout 线永远无法进池）。

## 替代方案

* **每个字段给默认值，缺字段就填默认**：就是这次的病灶。默认值让"没记录"与
  "记录了默认值"不可区分，而这两者在协议身份上是相反的意思。
* **把协议变量放在文件头（每局重复的字段只写一次）**：逐局记录是唯一能自证
  "这局怎么测出来的"的东西，而评分池按行 ingest（`ingest_jsonl`）。头部字段会让
  下游读不到它，除非再约定一套合并规则——多一层能漂移的东西。
* **用 `build_id` 代替 `protocol_version`**：见决策 5。重建导致假分裂的代价，
  远大于它多拦住的那些情形；真正需要拦的语义变更由版本号这个显式动作承担。
* **把 `games` 也放进协议**：不必要，且与池子的用法冲突。同一 seed 加大局数时
  前 N 局逐局不变（ADR 0016 已验证 400→800），所以 `games` 只影响区间宽度。
* **保留旧池并用启发式推断补齐字段**：推断出的字段会与真实协议不符，
  而池子存在的意义就是它记的协议是真的。

## 验证方式

* **跨语言字段对齐**：C++ `r2048 evaluate` 写出的逐局记录喂给 `build_protocol`
  必须零缺失字段。这条防的是"改了 C++ 写出方忘记改 Python 读者"这类漂移。
* **缺字段与类型**：只给 `{track, rules_version}` 的输入必须报错并列出缺的字段；
  `c_puct: 1` 与 `c_puct: 1.0` 必须得到同一个哈希（`json.dumps` 对二者字节不同，
  不归一化就会按写出方劈线）；`rules_version: 1.5` 必须报错而不是截断成 1。
* **写出方不影响引擎**（三条独立复核，全部逐局 400/400 一致）：
  * NN 线重跑 c2 臂：`eval --checkpoint runs/c2-policy/model.pt --track nn_mcts
    --simulations 64 --c-puct 1.5 --lanes 64 --in-flight 4 --games 400
    --seed 20262053 --label c2-nnmcts64` → 与既有 `eval/c2_nnmcts64.jsonl` 一致。
  * 纯线：`evaluate --policy random --games 400 --seed 20262053` → 与
    `eval/random_s20262053.jsonl` 一致；`--policy mcts --simulations 64` → 与
    `eval/mcts64_s20262053.jsonl` 一致。
    顺带记录一个反例的教训：第一版复核用了 `runs/c2-value/model.pt`，只对 1/400。
    那不是回归，而是拿错了检查点——c2 臂的检查点是 `c2-policy/model.pt`
    （`c2-value` 的价值路径相同、策略先验不同，搜索立刻分叉）。选检查点这件事
    在评测脚本里必须是显式参数，不能靠"哪个看起来像"。
* **新池重建后与旧文档口径一致**：用新格式重跑基线锚点与 c2 臂、清空重算，
  得到的数字与旧记录**在四舍五入误差内相同**（旧锚点文件把 `L_ref` 存成了 13.726
  这个三位小数，新文件存全精度，所以第三位小数后才分岔）：

  | 臂 | 旧池（pre-protocol/pool4.jsonl 重算） | 新池（新协议） |
  |---|---:|---:|
  | 纯锚点 `random` 的 `L_ref` | 9.913542 | 9.913542 |
  | 搜索锚点 `mcts64` 的 `L_ref` | 13.725968 | 13.725968 |
  | `c1-nnmcts64` 评分 | 967.688 | （未重跑） |
  | `c2-nnmcts64` 评分 | 1038.874 | **1038.881** |

  这条同时说明：旧池的那些数字**其实没有被默认值兜底污染**——所有臂恰好共用同一组
  `c_puct`/批组成，所以缺字段没有造成实际合并。这是运气，不是保证：
  换个 `--c-puct` 的实验就会静默并进同一条线。
* **`eval_seed` 出协议的效果**：同一模型、同一协议、两个 seed 的评测现在必须
  落进同一 `protocol_hash`（此前是两条线），而 `game_key` 仍然按 seed 去重。

## 尚未实施 / 尚未验证

1. **数据批（跑谱）的 manifest 侧还缺两个协议变量**：`params` 里没有
   `max_batch`，也没有 `device`（引擎不知道设备，由 Python 侧持有）。
   两者都实测能改变产出数据，因此一份跨设备的批次现在是一个"自己说自己同质"的假同质批次。
   修它需要让 Python 把引擎不知道的 provenance 传进 manifest——与跑谱续跑的
   参数比对（P2）一起做，否则续跑会用不同设备接着写同一批。
2. **命名不统一**：同一个旋钮在引擎与数据 manifest 里叫 `in_flight_per_lane`，
   在评测协议与 CLI 里叫 `in_flight`。
3. **纯 rollout 的探索常数仍没有入口**（ADR 0016 决策 4 缺口 C）：
   现在只能靠 `protocol_version` 归因，不能扫它。给它加 `--exploration`
   是一条独立的改动（要同时进引擎配置、CLI、pybind 与数据 manifest 的 `params`）。
4. **`nn_mcts` 不给 checkpoint 时会崩**（`evaluator` 为 `None`）：本次没有改动它，
   它既不是协议问题，也不影响任何已记录的读数。
5. **前协议记录不能再被分析**：`normalize_row` 现在会因缺字段报错，所以
   ADR 0016/0017 里那些逐局记录（`eval/sims-sweep-800/`、`eval/cpuct/` 等）
   **无法用当前代码重算**，那些曲线只能从文档里读，要重算就得重跑那些臂。
   这是有意的取舍（宁可拒绝，也不要用默认值伪造协议），但代价要记下来。
