# ADR 0019：作业目录、结构化进度与子进程封装

- 状态：已采纳
- 日期：2026-10-06

## 背景

跑谱、训练、评测都是几分钟到几小时的任务，而在这一条之前，**它们的进度只存在于
stdout 的一行 `\r` 里**，C++ 子命令的进度更是只在终端闪一下就没了。后果不是"不方便看"，
而是三件具体的事：

1. **外部观察者只能解析人类的打印文本**。任何脚本（更别说将来的界面）想知道
   "跑到哪了"都得对着 `\r` 覆盖的一行做正则，而那一行的格式是随实现改的。
2. **中断后没有现场**。进程被杀之后，除了终端回滚缓冲什么都不剩：
   跑到哪一步、用什么参数跑的、产出了什么，都要靠人回忆。
3. **C++ 调用方式散落**。`generate/evaluate/verify/bench` 没有 pybind，
   调用它们需要知道 CLI 在 `build/bin/`、需要设 `R2048_OUTPUT_DIR` 与 `PYTHONPATH`。
   这套知识当时只存在于 Makefile 与 `/tmp` 下的临时脚本里——一旦要自动化（或接界面），
   就得在第三个地方再抄一遍。

## 决策

1. **作业目录** `<输出根>/runs/<job_id>/`，四个文件各司其职：

   | 文件 | 内容 | 写法 |
   |---|---|---|
   | `job.json` | 这次跑的是什么：kind、参数、pid、构建身份（build_id / 规则与协议版本） | 进入时一次 |
   | `status.json` | 现在到哪了：state（running/finished/failed）、最后一次进度、已用秒数 | **原子重写**，每次进度 |
   | `log.jsonl` | 发生过什么：exec / stdout / progress / result / finished / failed | 只追加 |
   | `result.json` | 产物在哪（manifest 路径、checkpoint、协议哈希……） | 结束时一次 |

   `job_id` 标识**一次尝试**（`selfplay` 用批次号，`eval` 用 `<label>-<时间>`，
   `train` 用 `--output` 的目录名）。`JobDir` 用 `with` 进入/退出，
   因此正常结束写 `finished`、异常路径写 `failed`——不依赖调用方记得收尾。

2. **`status.json` 保持诚实**。进程被 `kill -9` 时没有任何代码有机会改写它，
   所以它保留的是**最后一次已知进度**、状态仍是 `running`。判断"作业是否还活着"
   是读者的事（比对 `pid`），这里不假装知道，也不在下次启动时去"修历史"。

3. **结构化进度**：`on_progress(payload)` 的字段固定（`r2048.jobs.PROGRESS_KEYS`）：
   `stage / done / total / unit / elapsed / rate / eta / line / extra`。
   两条设计上的取舍：

   * **`total` 可以为 None**，表示"不限量"——这正是跑谱要变成"跑到被停下为止"
     的形状（P2），进度条不能因为分母是"无穷"就消失。
   * **`line` 是给人看的**：阶段自己格式化，因为它知道该带哪些细节
     （批均值、显存、缓存命中率）。速率与 ETA 的算术只在 `progress_payload` 里算一次。
   没设回调时各阶段仍然打印那一行，所以 CLI 的输出与改动前逐字相同；
   CLI 与界面的分叉只在这一个点。

4. **子进程封装** `run_cpp(command, args, job=...)`：
   路径解析（`R2048_CLI`，否则从 `r2048_core` 的位置反推 `build/bin/r2048`）、
   参数拼装（下划线转连字符、`True` 作开关、`None`/`False` 省略）、
   输出逐行转发进作业日志，都收在一处。**输出根显式注入子进程**：
   C++ 侧读同一个 `R2048_OUTPUT_DIR`，但库调用方不该依赖"启动前 export 过"——
   两边算出不同的根，数据会写到两个地方而不报任何错。

5. **`r2048 probe` 的计算抽到 `r2048.runtime.probe`**，CLI 只负责排版。
   探针的定位不变（只前向、不选招，选招口径只有 C++ 引擎一处），
   抽出来是为了让界面与脚本复用同一条口径，而不是各自实现一遍"怎么看网络输出"。
   顺手订正了它的一处注释：`probe` 的开局用 Python 的 `random`，
   **不是**引擎的开局序列（引擎按 `derive_seed(...)` 派生），所以同一个 seed
   并不给出引擎第 0 局的开局——想复现具体局面应当直接传 `--board`。

## 理由

* **"随时可读"必须靠原子写**：`status.json` 存在的意义就是被别的进程读到。
  非原子写会让它有一段时间是半截文件，读者解析失败——而失败的时机恰好是
  "任务正在进行"这个最需要读它的时刻。Python 侧此前没有原子写，
  现在 `r2048.fileio` 与 C++ 的 `write_text_atomic` 同形（tmp + rename，都不 fsync：
  防的是进程级中断，不是断电）。
* **每行输出都进日志**：作业目录是排查问题的第一现场。把 C++ 子命令的输出只留在
  终端回滚缓冲里，等于放弃了现场；而 `run_cpp` 每行都记的代价可以忽略
  （跑谱的 stdout 是秒级一行）。
* **不做的事**：不做作业队列、不做并发调度、不做状态机重试。这些要有真实的
  并发需求（界面同时跑多个）时才做，现在没有。

## 替代方案

* **让 C++ 侧也直接写 status.json**：要把"作业"这个概念塞进每个子命令里，
  而 C++ 侧只需要知道它自己那一层（它已经写下数据 manifest 了）。
  由 Python 侧统一记账更简单，也让 C++ 保持可以单独用。
* **进度改用环境变量/命名管道传给外部观察者**：比读一个文件复杂得多，
  而且 `kill -9` 时一样什么都不剩。文件是这里最结实的通道。
* **把 `line` 去掉，只留结构化字段，展示交给调用方**：会让 CLI 的输出退化
  （阶段特有的细节——批均值、显存、缓存命中率——就得靠调用方猜），
  或者把格式化逻辑复制到每个调用方。
* **给 `status.json` 加"心跳超时自动置为 failed"**：需要外部守护进程，
  而且会与"读者自己判断"这条冲突——两个地方都能改状态，就没人知道哪个是真的。

## 验证方式

* **小规模评测**：`python -m r2048 eval --checkpoint ... --track nn_mcts --simulations 4
  --games 8` → `runs/eval-<label>-<时间>/{job.json,status.json,log.jsonl,result.json}`
  齐全，`status.json` 的 state 为 `finished`。
* **中断后仍可读**（这是本 ADR 的核心承诺）：起一次自对弈（`--samples 200000`），
  十几秒后 `kill -9`，`status.json` 必须是可解析的 JSON 且带最后一次进度——
  实测得到 `state=running`、`done=33253/200000`、`rate≈3161 样本/秒`、`eta≈52.7s`、
  `pid` 与 `elapsed`，`log.jsonl` 有 21 条事件（exec / progress）。
* **`run_cpp`**：`evaluate --policy random --games 8` → 退出码 0、
  `last_line` 是既有约定的汇总 JSON（ADR 0008）、日志里 stdout 逐行齐全。
* **`probe` 抽出后行为不变**：同一个局面打印的四个方向的合并得分 / A(u) / π 与
  抽出前一致（改动是搬移与排版，不是重算）。

## 尚未实施

1. ~~**C++ 子命令的进度还没有结构化**~~ **已实施**（ADR 0020 决策 10）：
   `Progress::set_json(stage, unit)` 让进度按行吐 JSON 到 stderr，
   `run_cpp(..., progress=True)` 把两条流分开读并把进度写进 `status.json` / `log.jsonl`。
   `generate` 与 `evaluate` 已用它；`verify` / `bench` 现在没有进度条，
   等它们有需要时再加。
2. **没有作业清单**。`runs/` 下有哪些作业、各自什么状态，现在要靠 `ls` +
   逐个读 `status.json`。等界面真的需要"作业列表"时再加一个索引文件
   （而不是提前维护一个可能与目录不同步的清单）。
3. **`train` 的 `--output` 与 `runs/<job_id>` 是同一处**，但 `eval` 的产物
   （`--jsonl`）与作业目录是分开的两处。这不一致，但反映了事实：评测的产物是
   "一组逐局记录"，它可以落在任何地方（评分池会去 ingest 它），
   作业目录只是那次跑的过程记录。
