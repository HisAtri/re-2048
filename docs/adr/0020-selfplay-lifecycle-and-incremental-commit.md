# ADR 0020：跑谱生命周期与增量提交（不限量 / 暂停 / 继续 / 终止）

- 状态：已采纳
- 日期：2026-10-07

## 背景

在这一条之前，跑谱是一次性的，四处硬约束把它钉住了：

1. `generate` 强制 `samples_target > 0`（不设目标就报错）；
2. 停止只有进程内的 atomic，没有外部通道，也没有任何信号处理；
3. 输出目录必须为空，局号从 0 起且写入侧强制递增（`shard.cpp` 的局号校验）；
4. **manifest 只在结尾写一次**，所以"这一批写完了没有"只能靠"文件在不在"回答。

后果是具体的，不是"不方便"：想多要一点数据只能整批重跑；长跑无法把机器让出来
（GPU 排队、白天要用机器）；中途被杀不但丢尾部，连"跑到哪了"都没有记录；
跑谱与训练的衔接只能靠人盯着"够了没有"，而"够了"在文件里没有任何表示。

用户在收尾计划里的第 4 项要求：**不限局数 + 随时暂停 / 继续 / 终止**。

## 决策

1. **不限量**：`samples_target == 0` 表示跑到被叫停为止（纯 C++ `generate` 与批推理引擎
   的 NN 路径都改）。原先"截断最后一局以恰好命中目标"的逻辑只在目标 > 0 时生效——
   不限量时一局要么整局落盘，要么不落。

2. **控制通道有两条入口，一套语义**：

   * **控制文件**（默认 `<数据批目录>/control`，可 `--control` 指定），内容是 `pause` 或 `stop`。
     **一次性**：被消费后删除，所以续跑不会立刻又被同一条指令叫停；无法识别的内容
     每换一个新值报一次错并忽略（静默忽略会让用户以为"按下了停止"而进程还在跑）。
     主循环每 ~200ms 轮询一次，轮询在 `Control` 内部节流。
   * **信号**：纯 C++ 的 `generate` 装 SIGINT/SIGTERM 处理器，等价于 `stop`；
     NN 路径跑在 Python 进程里，Ctrl-C 是 Python 的 `KeyboardInterrupt`，
     由 `run_selfplay` 捕获后调 `request_stop()`。两条路都落到同一处停车语义。

   不用信号作为唯一手段：文件通道对 C++ 与 Python 一致、可测试、界面也能写。

3. **停车点只有"局与局之间"**。进行中的局一定走完，已产出的数据一定被提交。
   这不是礼貌，是正确性要求：按局号顺序落盘的写入侧会卡在局号缺口上
   （`batched_engine.cpp` 里已实测踩到过）。

4. **manifest 是增量提交日志，不是结尾标记**。每落一个分片就原子重写一次，
   内容是 `state`（running / paused / stopped / complete）+ 累计 `samples` / `episodes`
   + 分片表。**它列出的分片才有效**：被 SIGKILL 只会留下"已落盘但未被列出"的孤儿分片，
   而读侧（`BatchReader`）本来就只遍历清单里的分片，所以孤儿不污染任何东西，
   续跑时会被按同样的内容重写一遍。

5. **分片只在局边界上切**（`kShardLayout = 2`，写进清单）。攒满容量之后的第一局末尾才落盘，
   于是末片永远结束在一局的末尾，`manifest.episodes` 恒等于 `last_episode + 1`，
   不存在"半局"这种状态。代价是分片可以略微超过容量（最多多出一局），
   对读取侧完全透明。旧规则（精确容量，layout 1）会切在局中间，因此**旧批拒绝续写**：
   续写会让同一批数据出现两种分片布局，而那正是"逐字节复现"依赖的东西。

6. **继续 = 就地追加同一批**（用户已确认的边界）。`--continue` 读 manifest，
   从 `manifest.episodes` 接着编号；**末片不满就把它读回缓冲继续填**，而不是新起一片——
   否则分片边界会从停车点偏移，后面的每一片都跟着变。

7. **续跑的参数闸门逐项比对，不做摘要比对**。比对 `seed / policy / simulations /
   temperature_moves / model_id / build_id / shard_samples` 与在 `kProtocolParams`
   里声明过的协议参数（`c_puct / lanes / in_flight_per_lane / temperature /
   cache_entries / max_batch / device`），不一致就**指名道姓**拒绝
   （"seed 原为 888，本次为 999"）。摘要只能告诉你"不一致"，而这里要的是"哪一项变了"。
   非协议参数（`--samples / --workers / --out / --control`）允许变化：
   它们只是"当时是怎么敲的命令行"的记录。
   `build_id` 与**编译期常量**比对：换二进制续跑意味着前后两半出自不同的搜索实现。
   跑完（`complete`）的批次拒绝追加——追加数据应当新起一批（多来源见 ADR 0021）。

8. **续跑时 `--samples` 是整批的累计目标**。判定用的是"已提交条数 + 本次产出"，
   所以"跑到 6000 条"在续跑里就是"这一批到最后有 6000 条"。

9. **被丢弃的前向批必须能补发**（实测挖出来的协议补丁）。`advance` 发出、
   却没有被 `submit` 回填的请求，在下一次 `advance` 时重新排队。没有这一步，
   一次被丢掉的前向（Ctrl-C 恰好落在前向里、Python 回调抛异常、显存不足）
   会让这些 lane 永久挂住：**待发队列已空、lane 又没有收工**，调用方拿到的是
   "既没有请求、也没有结束"。请求本身可重放（同一个局面、同一份搜索状态），
   重发是唯一正确的补救。正常路径下这里是一个空循环。

10. **C++ 子命令的进度结构化**：`Progress::set_json(stage, unit)` 让进度以 JSON 行
    写到 **stderr**（stdout 只留可被管道消费的最终结果，ADR 0008），
    `jobs.run_cpp` 把两条流分开读、把进度行解析成结构化 payload 交给作业状态文件。
    这补上了 ADR 0019 里"尚未实施"的第 1 条。

## 理由

* **为什么清单要变成提交日志**：一次几小时的长跑被杀在最后一分钟，丢掉全部数据是不可
  接受的；而每落一片重写一个几 KB 的 JSON 的代价可以忽略。副产品是"这批到底跑完了没有"
  第一次有了答案（此前只能靠"manifest 在不在"）。
* **为什么按局边界切**：这是"暂停再继续产出的批次与一次跑完逐字节相同"的**必要条件**。
  精确容量切分让分片边界取决于容量计数，而停车点会把一个分片提前落盘，
  于是边界从停车点漂移——数据内容没错，但逐字节比对的判据没了。
* **为什么参数闸门要指名**："参数不一致"这句话在用户那里无法行动；
  "seed 原为 888，本次为 999"可以。这也是同一条原则在 ADR 0018（缺字段必须报错）
  上的延续。
* **诚实的一条：逐字节相同这条判据只在纯 C++ 轨迹上成立**。NN 自对弈的叶值来自批推理，
  而批组成会改变浮点归约顺序（ADR 0017）；实测同一个局面在 batch=1 与 batch=64 下
  的 value 相差 ~8e-7。续跑进程的 lane 种群、推理缓存与前向批次与前一次运行天生不同，
  所以**尾部可能不同**。实测：lanes=8、6000 条目标下，一次跑完 55 局、停+续 54 局，
  逐局比对有 10 局不同；lane=1 时差异缩小到 29 局里 3 局（并发越少越接近一次性）。
  但"同一个停车点续跑两次"是逐字节相同的（实测 B/C/C2 三方哈希全等）。
  所以 NN 路径的承诺是：**前缀逐字节相同 + 给定停车点可复现 + 结构合法可训练**，
  而不是"等于一次跑完"。要拿到强逐字节性质只有一条正道：让叶值与批无关
  （每次前向补齐到固定行数），代价是吞吐——现在不做，记在这里。

## 替代方案

* **每次续跑新起一批**：用户已否。旧池子那套"多批次 + 事后合并"把身份问题推给了训练侧，
  而 ADR 0021 要处理的身份问题本来就够多了。
* **用哈希/摘要做续跑参数闸门**：说不清是哪一项不同，见上。
* **用命名管道或 socket 做控制通道**：比一个文件复杂得多，还引入"谁先连上"的时序问题；
  控制文件在 `kill -9` 之后依然可读、可写、可测试。
* **只有信号、没有控制文件**：SIGINT 在 Python 侧是异常、在 C++ 侧是处理器，
  两种语义要想在界面上用还得再包一层；文件通道是跨语言最结实的那个。
* **给控制文件做版本化协议（JSON 指令 + 参数）**：现在只有 pause/stop 两个词，
  JSON 只会让 `echo stop > control` 这个最好用的形态失效。
* **把叶值做成与批无关**：见上，代价是吞吐；ADR 0017 已经接受了批组成依赖这个事实，
  这里只记录它带来的后果边界。

## 验证方式

* **C++ 单测**（`cpp/tests/test_dataio.cpp`）：`dataio_pause_resume_matches_oneshot`
  覆盖两种停车点——末片恰好满（续跑必须新起一片）与末片不满（续跑必须读回来接着填）——
  断言续跑与一次跑完的**逐片哈希相同**；`dataio_resume_refuses_other_source`
  断言换 seed / 换 device / 改 shard_samples / 旧 layout / 已 complete 各自被拒绝
  且消息里带上了那一项的名字。
* **C++ 单测**（`cpp/tests/test_engine.cpp`）：`engine_requeues_dropped_batch`
  丢掉一整批回填后引擎仍然跑完，且 `requests_issued == requests_submitted`。
* **纯 C++ 端到端**：mcts64、`--shard-samples 4000`、目标 40000，
  A 一次跑完 vs B 跑一半→`stop`→`--continue`，**逐片（条数, 哈希）完全一致**；
  两批都用不同的 worker 数跑 `verify --replay` 通过（同时证明布局与线程数无关）。
* **控流**：`echo stop > <批目录>/control` → 退出码 0、`state: stopped`、控制文件被删除；
  `pause` → `state: paused`；`kill -INT`（纯 C++）→ 优雅停车且数据已提交。
* **NN 路径**（Python CLI，`--samples 0` + control + `--continue`）：停到 2923 条 /
  28 局（末片 895 条），续跑到 6000 条 / 54 局且 `state: complete`；
  同停车状态续跑两次（B、C、C2）逐片哈希全等；与一次跑完的差异按局定量（54 局里 10 局）。
* **批组成依赖的直接测量**：同一局面在 batch=1 与 batch=64 下 value 差 ~8e-7、
  policy 差 ~2e-7（CPU，torch 2.14）。
* **Ctrl-C 落在前向里**：修复前表现为 `RuntimeError: 自对弈卡住`（引擎挂住、只能弃批），
  修复后打印"收到 Ctrl-C：正在停车……"、走完进行中的局、`state: stopped` 且数据已提交。
* **`--progress-json`**：`r2048 evaluate ... --progress-json` 的 stderr 上是
  `{"progress":{stage,done,total,unit,elapsed_ms,rate,eta_seconds,line}}`，
  stdout 末行仍是汇总 JSON；`jobs.run_cpp(..., progress=True)` 把它写进
  `status.json` 与 `log.jsonl`（秒为单位换了一次）。
* **尚未验证**：Python 路径下的 SIGTERM（没有装处理器，进程立即退出）——
  已提交的数据不受影响是结构性保证（清单是提交日志），未落盘的那一屏由续跑重算，
  但没有单独实测；第二次 Ctrl-C 的硬退出路径也未单独实测（`finally` 仍会提交已产出的数据）。
  纯 C++ 路径的 SIGTERM 走的是优雅停车（`generate` 装了处理器，已随 `kill -INT` 一起实测）。
