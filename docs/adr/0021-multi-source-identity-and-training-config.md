# ADR 0021：多来源数据身份与训练配置

- 状态：已采纳
- 日期：2026-10-07

## 背景

训练的下一步是"用自己产出的多批数据训练"（课程学习、新旧数据混合、把搜索数据小比例
混进随机数据池）。在动手之前有一个必须先解决的坑：

**`episode` 是批内编号（0..N−1）**。`teacher-s256` 与 `teacher-s1024` 都用 seed 20261020，
两批数据的局号都从 0 开始，而它们的第 7 局是两局完全不同的棋。把两批数据拼起来之后：

* 按局划分（ADR 0009）用的是 `hash(episode, seed)` → 两个来源的同一个局号总是被分到同一侧，
  于是"来源 A 的第 7 局在训练集、来源 B 的第 7 局在验证集"这种切法永远不会出现——
  验证集里混进了训练时见过的**同一棋谱的另一批采样**（同一个种子的同一局，被搜索预算
  不同地展开），干净程度远不如设计意图；
* 按局统计（"训练了多少局"）会把两个来源的同号局算成一局，日志上的局数直接是错的。

另一个更基础的问题：合并多批数据需要**来源的身份**，而目录名、批次号都不合适——
就地在同一批上续跑（ADR 0020）会让目录内容一直变，搬目录则会让身份凭空改变。

同时，训练参数此前散在 27 个 CLI 参数里，且没有任何"这条训练线是什么"的可命名实体；
迭代编排（ADR 0022）与续跑闸门（P3b）都需要一个能被引用、能被记进 checkpoint 的配置。

## 决策

1. **来源身份 `source_key` 由 provenance 字段算出**（`shards.source_identity`）：
   `policy / simulations / temperature_moves / seed / model_id / build_id` + 协议参数
   （`c_puct / lanes / in_flight_per_lane / temperature / cache_entries / max_batch / device`）
   + `schema_version / rules_version / protocol_version`。
   **不含** `samples / episodes / state`（续跑会一直改它们，而续跑前后按定义是同一个来源），
   **不含**路径与批次号（搬家、改名不该换身份）。同一份摘要给两个形式：
   十六进制的短标识（给人看、写进日志与产物）与 64 位数值（供向量化的按局哈希）。

2. **划分对 `(source_key, episode)` 判定**，逐来源划、再聚合。两条直接推论都要成立：
   * 加一个来源**不改变**任何已有来源的训练/验证归属（否则每加一批数据都得整体重训才能对比）；
   * 同一个局号落在哪一侧**由来源决定**，"同种子同局号"不再被判成同一局。

3. **合并视图是一个连续的下标空间**：各来源首尾相接，`SourceView` 记 `(offset, samples)`。
   刻意**不**维护"每条样本属于谁"的数组——来源是连续区间，`searchsorted` 一次就够，
   而那份数组在千万级样本上是几十 MB 的净浪费。

4. **权重语义是"每轮按权重分配采样配额"，不是"每个来源跑几遍"**：
   `samples_per_epoch`（默认 = 各来源**训练池**之和）按 `quota_i ∝ w_i · pool_i` 用最大余数法
   分成整数配额。配额超过池子时**有放回**采样：小池子被指定了高权重时，"抽满配额"
   比"悄悄缩水"更符合配置的字面意思，也更容易被看见。
   单一有效来源退化成整池 `permutation`——一个随机数都不多用，所以单批用法与 P3a 之前同形。

5. **权重 0 等于没列这个来源**（用户可依赖的等价关系）：它不参与 `samples_per_epoch`、
   也不消耗随机数，因此**训练曲线与"不列它"逐张量相同**。同理，"重复列同一个来源"
   不按"权重相加"处理，而是按 `source_key` 去重并告警：重复项意味着同一个身份会被算两次，
   那是配置写错了，不是特性。

6. **`limit` 按条截断**（0 = 不限），允许切在一局中间。按局的保护针对的是"整局都在池子里"
   的情形；被截断的尾局不会出现"同一局一半在训练一半在验证"。

7. **训练配置用 YAML，且只有训练用**（用户已确认的边界）：YAML 声明
   `datasets: [{path, weight, limit}]` 与 `train:`（与 `TrainConfig` 同名的字段）。
   合并优先级 **CLI > YAML > 默认值**，靠 argparse 的 `SUPPRESS` 默认值实现——
   只有显式给出的参数才在 namespace 里，"用户到底指定了什么"因此是精确可知的。
   跑谱、评测、评分仍然只有 CLI。`--data` 与 YAML 的 `datasets` 同时给出时以 `--data` 为准
   （编排要用同一条训练线的参数去训新跑出来的批次）。

8. **`config_digest` 覆盖这份配置（含数据集与权重），但排除运行期回调**。
   回调是运行期接进来的（结构化进度，ADR 0019），不属于配置：它进不了 JSON，
   混进去会让"走 CLI 的每一次训练"在第一次写 checkpoint 时崩掉。

9. **验证集为空是显式失败**，除非调用方写明 `val_fraction=0`。
   空的验证集不会报错，只会把所有验证指标变成 NaN、把"最佳 checkpoint"变成永远选不出来
   （实测：5% × 50 局的批次有约 8% 的概率一局都选不进验证集，这个坑是在改身份时被撞出来的）。

10. **数据身份逐来源落进产物**：`train.json` 的 `data.sources`（身份、权重、条数、局数、
    协议、`state`）与逐来源的 manifest sha256；checkpoint 元数据里的 `sources`。
    单来源时**同时**保留 `batch_id` / `data_build_id` 两个历史键（评测脚本与旧产物比对在用），
    多来源时它们为空——不挑一个来源冒充整体。

## 理由

* **为什么身份要算出来而不是记下来**：身份必须是"谁、用什么协议产出的"这一事实的函数，
  才能满足两个都实际发生过的要求——就地续跑（ADR 0020）与搬目录。记一个批次号或路径，
  这两件事都会把同一份数据变成"新来源"。这也与 ADR 0020 决策 7 的分工一致：
  C++ 侧的 `kProtocolParams` 管**续跑闸门**（这次参数与上次同不同），
  Python 侧的 `SOURCE_KEY_PARAMS` 管**身份**（两批数据是不是同一个来源），
  两处都只关心"会改变逐局结果的参数"，所以两个清单同源、但用途不同。
* **为什么用逐项比对而不是摘要**：与 ADR 0020 决策 7 同一个理由——
  "来源不同"这句话在用户那里无法行动，"simulations 原为 256，本次为 1024"可以。
* **为什么把局数逐来源报出来**：只报总数会掩盖最常见的配置错误——某个小来源
  整批进了训练集、在验证集里一局都没有。日志里看得见，就不用等指标异常再去猜。
* **诚实的一条：切分口径变了**（身份里多了来源），因此**P3a 之前的训练曲线与之后的
  不再逐轮可比**：同样的 `(val_fraction, split_seed)` 选出的验证集不同。这是把来源折进
  身份的必然代价，而不是可以绕开的选择；记在这里，避免日后拿两份曲线对比时以为是回归。
* **为什么权重 0 要做成"不存在"**：这是唯一能让"关掉一个来源"变成可验证操作的语义。
  如果权重 0 仍然参与每轮长度或消耗随机数，那"加了但权重 0"与"没加"就会给出两条曲线，
  而两条都"看起来合理"——这种差异只能靠逐张量比对发现，不值得让用户去发现。

## 替代方案

* **用目录名 / 批次号做来源身份**：搬目录或就地续跑会换身份，见上。
* **把 `episode` 在合并时重编号**（来源 1 的局号 + 偏移）：能避免串线，但会让"局号"
  变成读入顺序的函数——同一批数据换个顺序读入就换了身份，与按局哈希划分的初衷（顺序无关）冲突。
* **权重语义用"每个来源跑几遍"**：无法表达"把新数据小比例混进大池子"这种最常见的用法，
  而这正是多来源的第一需求。
* **`weight: 0` 直接报错、让用户删掉那一行**：用户的意图是"暂时不用这个来源"，
  报错会变成强迫编辑文件；而"0 = 不列"这条等价关系是可验证的（见验证方式）。
* **给跑谱 / 评测 / 评分也写配置文件**：用户已否。它们的参数是"这一次动作"的属性。
* **在训练里给每个来源单独跑一遍 epoch**：会让"一个 epoch"的含义随来源数变化，
  学习率日程与进度显示都会跟着变得难以解释。
* **逐样本的来源数组**：千万级样本上白占几十 MB，而来源本来就是连续区间。

## 验证方式

* **`python/tests/test_data_and_training.py::test_merging_sources_does_not_change_either_split`**：
  同 seed、只差 `simulations` 的两批（`mcts --simulations 8` 与 `16`，seed 424242，
  这正是 `teacher-s256` / `teacher-s1024` 的形态）合并后，
  ① 两个来源的身份不同；② 逐来源切片与"单独划这一批"的结果**逐下标相同**；
  ③ 存在某个局号在一个来源里是验证、在另一个来源里是训练——身份里没有来源时，
  这条断言永远找不到反例。
* **`test_multi_source_split_has_no_leakage`**：以 `(来源, 局号)` 为身份，
  训练集与验证集的交集为空；逐来源的训练/验证局数非零且加总一致。
* **`test_weight_zero_source_leaves_the_curve_identical`**：
  `[A 权重 1.0]` 与 `[A 权重 1.0, B 权重 0.0]` 两次训练，
  **逐张量 `torch.equal` 相同**、逐轮训练损失相同。
* **`python/tests/test_train_config.py`**（7 条）：CLI 覆盖 YAML、YAML 覆盖默认值、
  `--data` 覆盖 YAML 的 datasets、缺数据被拒、拼错小节/字段/数据键/`on_progress` 各自报错、
  摘要随超参与权重变化且不受回调影响、文档里那份样例配置真的能读进来。
* **端到端**（`train --config`，CPU）：`random`(4000 条/29 局) + `mcts8`(6000 条/14 局)，
  权重 1 : 0.5 → 每轮 5873 条（配额 3915 / 1958，正好 2:1），
  `val_fraction=0.3` 逐来源报出（18/11 与 7/7）；
  `--epochs 3` 覆盖 YAML 里的 2；产物里 `data.sources`、逐来源 manifest sha256、
  `config_digest`、`model_id=value-2src` 都在。
* **`limit` 截断**：把来源截到 1000 条后，该来源报 7 局、全局下标空间与 `gather` 一致。
* **尚未验证**：两个大池子（各百万级）按权重混合时的吞吐与显存行为；
  "小比例混入是否真的提升棋力"是实验问题，属于迭代阶段（ADR 0022）而不是本条的验收。
