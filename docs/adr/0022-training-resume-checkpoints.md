# ADR 0022：训练断点续跑（批级 checkpoint 与随机数状态）

- 状态：已采纳
- 日期：2026-10-07

## 背景

训练此前"崩一次白干一轮"。具体缺口有四处，每一处单独看都像小事：

1. `last.pt` **只在每个 epoch 末写一次**，epoch 内崩掉这一轮的全部计算就丢了；
2. **随机数状态一个都没存**（torch 全局、CUDA、numpy、D4 增强用的 `torch.Generator`），
   所以即使恢复了模型也无法接着跑出同一条轨迹；
3. `best_metric` **不持久化**，续跑后被置 `None`，于是最佳 checkpoint 的选择重新计分
   （一次更差的轮会覆盖 `model.pt`）；
4. 恢复路径用裸 `torch.load` **绕过元数据闸门**，`torch.save` 也直写目标路径
   （写一半被读走就是随机位置崩）。

用户在收尾计划里的第 5 项要求：**跑谱与训练的 Checkpoint 机制**。跑谱侧已由 ADR 0020
解决（增量提交 + 就地续跑）；这一条解决训练侧。

## 决策

1. **checkpoint 版本 2**：内容 = 模型 / 优化器 / 调度器状态 + `epoch` / `step_in_epoch` /
   `global_step` + **随机数状态** + `best_metric` / `best_metric_kind` + `config`
   + `data_identity` / `data_samples` + `history`。写入走 `tmp + rename` 原子替换。
   `step_in_epoch` 是"这一轮已经训过多少批"，它是续跑能精确回到批边界的唯一依据。

2. **保存时机有两条触发**：`--save-every-steps N`（按步数，适合可预期地控制"崩了丢多少"）
   与**时间兜底**（`SAVE_INTERVAL_SECONDS = 600`）。默认只开后者：按步数保存的代价是
   每 N 步写一份几十 MB 的文件，而长跑（每轮几小时）里时间兜底才是有用的那个。

3. **轮内续跑 = 跳过前 k 批，而不是重训**。`_run_epoch(skip=k)` 在增强**之前**跳过：
   跳过不能消耗随机数，因为 checkpoint 里的随机数状态正是"第 k 批之前的"状态。
   数据顺序由 `(seed, epoch)` 完全决定（ADR 0009），所以"跳过前 k 批"之后看到的
   就是当时那些批。**这一步是"续跑等于一次跑完"的全部机制**：重训会让参数被更新两次。

4. **恢复闸门分两段，拒绝与告警的界线是"能不能解释"**：
   * **数据身份**（来源 `source_key` 列表 + 权重 + `val_fraction` + `split_seed`）
     不一致 → **拒绝**，并打印两边是什么。换数据接着训是静默错误：划分与标签口径都变了，
     而损失照样下降。想换数据就换一个 `--output` 新起一条线。
   * **其余配置**不同 → **逐字段列出来**（"`epochs: 8 → 12`"）后继续。把轮数调长是正常操作。
   * 数据身份**刻意不含**样本数与路径：批次会原地增长（ADR 0020），换个目录挂同一份数据
     也不该被当成换了数据。样本数变化只提示（"池子变了，划分可能与上一段不同"）。

5. **`best_metric` 与它的**口径**一起恢复**（`best_metric_kind`：`val_value_mae` /
   `val_candidate_best_hit` / `val_policy_ce`）。口径不同（换了配方，或换了一批没有候选监督
   的数据）时丢弃旧值并说明——拿两个量纲不同的数比大小会安静地锁死最佳选择的进度。

6. **学习率以配置为准，而不是以 checkpoint 为准**。恢复调度器会把 `base_lrs` 一起恢复，
   于是配置里的 `lr` 会被**悄悄忽略**（实测：把 lr 从 1e-3 改成 1000 续跑，实际仍按 1e-3
   训练，验证指标一模一样）。所以恢复后按配置重算当前步位置上的学习率：
   `lr = config.lr × 日程(恢复后的步位置)`。**不能**直接把 `lr` 设成 `config.lr`——
   调度器保存下来的 lr 已经是"基准 × 日程"的值，直接覆盖会让续跑的第一步少乘日程因子
   （这个错法被逐张量比对抓到过）。同一个 lr 时它是一次恒等运算，不影响逐张量复现。

7. **续跑时 `best_checkpoint` 从盘上恢复**：接续的是一条线，所以"当前最佳"就是上一段选出的
   `model.pt`。不恢复它会让"这一段没有哪一轮更好"时的返回值是空串，而调用方
   （CLI 的末行、迭代编排）会把空串当成"这条线没有最佳模型"。

8. **原子写统一走 `fileio.save_torch_atomic`**（`model.save_checkpoint` 也改用它）。
   防的是进程级中断，与 C++ 侧的 `write_text_atomic` 同一口径；不加 `fsync`。

9. **版本 1 的 checkpoint 仍能续跑**：它没有随机数状态与批内位置，于是从**轮首**继续，
   并明确打印"这份 checkpoint 没有随机数状态，从第 N 轮轮首继续"——
   以前的行为是默认值，现在它变成了一条有说明的降级路径。

10. **接受的一处不一致（明写）**：被打断的那一轮，它的 `history` 条目只统计**续跑的那一截**
    （训练损失与验证指标都是tail 的平均），所以该轮的条目不等于"一次跑完"的同一轮。
    后续各轮与最终权重逐张量一致。做到完全一致需要把指标累加器也存进 checkpoint，
    而它只影响日志可读性、不影响训练结果，不值得。

## 理由

* **为什么"跳过"而不是"重训"**：这是唯一能让续跑与一次跑完逐张量一致的写法。
  重训那 k 批会让参数被更新两次，其后的一切都不同——而那正是"崩一次白干"的另一种形式。
* **为什么必须存增强发生器的状态**：增强的旋转/镜像下标是训练输入的一部分。
  只恢复模型、重新播种生成器，等于用另一组随机变换继续训练——轨迹必然分叉，
  而这一点在损失曲线上看不出来。
* **为什么拒绝数据变化、却只警告配置变化**：用户改配置有明确的正当理由（把轮数调长），
  改数据没有——那等于换了实验对象，应当新起一条线（与跑谱侧"参数变了就是另一个来源，
  应当新起一批"同一条原则，见 ADR 0020 决策 7）。
* **为什么闸门不用摘要**：与 ADR 0020 / 0021 同一理由——"不一致"无法行动，
  "`lr: 0.001 → 10.0`"可以。

## 替代方案

* **只从轮首续跑**（把轮内进度丢掉、重训那一轮）：实现更简单，代价是"续跑 ≠ 一次跑完"
  且丢掉至多一轮的计算。用户在计划里明确要求"逐张量一致"，所以不取。
* **每步都落盘**：几十 MB × 步数，IO 会把训练拖慢；按步数与时间两条触发已经覆盖了
  "崩了丢多少"的需求。
* **不存 RNG，改用"重新播种 + 从轮首开始"**：轨迹与一次跑完不同，等于承认不可复现。
* **把指标累加器也存进 checkpoint**：见决策 10。
* **在配置里记"是否 resume"来决定闸门松紧**：配置不是闸门的状态源，checkpoint 才是。

## 验证方式

* **`test_resume_matches_one_shot_bitwise`**（`python/tests/test_data_and_training.py`）：
  每轮 8 批的配置下，A 一次跑完 4 轮；B 在**第 2 轮第 3 批**被中断（进度回调抛异常，
  而回调在落盘之后被调用，所以 checkpoint 恰好停在那个批边界上）→ 同样的配置加
  `--resume` 跑完。断言：`(epoch, step_in_epoch) == (1, 3)` 真的停在批边界上、
  `rng.augment` 在 checkpoint 里、**逐张量 `torch.equal` 与 A 相同**、
  其余各轮的训练损失与验证误差逐项相同（被打断那一轮除外，见决策 10）。
* **`test_resume_refuses_changed_data`**：同一个 `--output` 换成另一批数据 → 报"数据身份"并拒绝；
  换数据 + 换目录 → 正常跑（`resume` 指向空目录不去读 `last.pt`）。
* **`test_resume_warns_about_config_change`**：改 `lr` 续跑 → 打印"配置与上一段不同"且列出 `lr`，训练继续。
* **`test_resume_keeps_best_selection`**：第一段 2 轮 → 续跑第 3 轮用 `lr=0`
  （模型全是 GroupNorm，没有会自己漂移的状态，所以这一轮不改变参数、不构成"改善"）→
  断言验证指标与上一轮完全相同、`best_metric` 原样沿用、`model.pt`**没有被重写**
  （它的 `config_digest` 还是第一段的）。重启挑选的实现会重写它，所以这条测试是有判据的。
* **端到端（CLI）**：多来源 YAML（`random` + `mcts8`，权重 1:0.5）跑 2 轮 →
  `--epochs 4 --resume`：日志显示"从第 3 轮轮首继续"，第 4 轮跑完后
  `best_checkpoint` 指向真实存在的 `model.pt`（该段没有更好的一轮，验证决策 7），
  `result.json` 与 `status.json` 一致；`--save-every-steps 2` 时每 2 步落盘一次。
* **尚未验证**：
  1. **GPU 上的逐张量一致**。CPU 已测（本机 16 核 WSL2）。CUDA 上浮点归约顺序、
     cuDNN 算法选择（`benchmark` 默认为关）都可能引入差异，未实测；
  2. **真被 SIGKILL 打断**（落在两次保存之间）。丢一个保存间隔是结构性保证
     （保存是批边界 + 原子替换），但没有单独实测；
  3. **时间兜底（600 s）**：所有测试都走 `--save-every-steps`，时间路径未单独触发过；
  4. **CUDA 的 `torch.cuda.get/set_rng_state_all`** 分支没有 GPU 环境验证。
