# ADR 0023：迭代编排（薄驱动、步骤标记与半模型合并）

- 状态：已采纳
- 日期：2026-10-07

> 自动命名、显式续跑及 `publish` 步骤由 [ADR 0048](0048-automatic-identities-and-data-lineage.md)
> 更新。当前默认顺序为 selfplay → train → publish → evaluate → rate，下文保留历史背景。

## 背景

迭代从第二轮起就不是"跑一条命令"：跑谱产出新数据、价值头与策略头分开训练、把两半合并、
评测三条 track、把结果并进评分池。此前这套流程是 `/tmp` 里的 shell 脚本，里面混着三类东西：

1. **能被代码固定下来的约定**：批次路径靠 `tail -1` 从 stdout 里抓再 `dirname`；
   两个半模型的合并是一段 `PYTHONPATH=... python - <<EOF` 的内联 heredoc；
   评测协议参数散在命令行、注释与"上次是这么敲的"之间。
2. **必须每次都重新决定的东西**：这一轮跑多少局、用哪个模型当对手、评哪几条臂。
3. **失败后的恢复方式**：脚本从第一步开始跑，中间某一步失败就得整条重来
   （而跑谱与训练都是几十分钟量级）。

用户在收尾计划里的第 2 项要求：**把迭代编排正式化**。同时坚持的边界是：
跑谱、评测、评分各自保持独立 CLI（不合并成一条流水线命令）。

## 决策

1. **`r2048 iterate` 是薄驱动，不是新机制**：四步各自都是对既有入口的一次调用
   （`run_selfplay` / `run_training` / `run_evaluation` / `rating.ingest_jsonl`），
   没有任何一步在 iterate 里重新实现。**任何一步都能用原来的 CLI 单独重跑**——
   迭代失败时不该只有"重跑整个迭代"一个选项。

2. **四步的规范顺序固定**（`selfplay → train → evaluate → rate`），`--steps` 只能挑选、
   不能重排：后一步的输入是前一步的产物。跑谱的**目标样本数必填**（`--samples > 0`）：
   不限量是"人守着终端"的形态（ADR 0020），不是流水线的形态。并行度由 `--data-workers N`
   （默认 4）决定：起 N 个单线程 worker 进程写同一批（可复现，ADR 0031），目标按整批判定，
   所以**改进程数不影响产出规模**（ADR 0029 的订正）。

3. **幂等靠步骤标记**：每步做完写 `<迭代目录>/steps/<步>.json`，记录这一步产出了什么。
   重跑时跳过已完成的步骤；`--force` 重做。标记还有第二个作用——**只重跑后面的步骤时，
   前面几步的产物路径从标记里读**，不必让人重新敲一遍（"评测结果不满意，只重跑评测"是
   最常见的动作）。

4. **迭代目录自包含**：`iteration.json`（这次迭代的全部参数）、`steps/*.json`、
   `runs/{value,policy-head,policy}`、`eval/*.jsonl`、`rating.json`，加上 P1 的
   `job.json`/`status.json`/`log.jsonl`。逐局记录**不写进全局 `eval/`**——
   否则第二次迭代会覆盖第一次的基线记录，"那次迭代评了什么"就查不到了
   （首次实现踩到过这一点）。数据批仍然是全局的 `<输出根>/data/<批次号>`
   （它有自己的命名约定，且是评分与训练共同引用的实体）。

5. **训练配方写在驱动里，但每一步都是显式的**：价值 run → 策略 run（`freeze_value`，
   起点是上一轮的完整模型；首轮则是刚训好的价值模型）→ 合并。种子取 YAML 里的
   `seed` 与 `seed+1`（两个 run 必须是不同的采样/增强序列，而把两个种子都塞进 CLI 只会让
   YAML 里的 `seed` 失去意义）。数据集 = YAML 的 `datasets`（已有的池子，ADR 0021）
   **加上这一轮新产出的数据**（按 `--data-weight`）；YAML 里可以不写任何来源——
   首轮就是这么用的。

6. **协议变量统一注入并记录**：跑谱、NN 评测与基线评测共用同一套
   `simulations / lanes / in_flight / c_puct / device`，评测再加 `games / seed`，
   一并写进 `iteration.json` 与 `evaluate` 的标记。**基线臂每次迭代都在同一协议下重评**
   （默认 `random` 与 `mcts64`），因为它们同时是评分池锚点的数据来源——锚点停留在
   很久以前那次运行上，就等于尺子生锈了。

7. **半模型合并成为显式步骤**（`r2048 merge-halves` + `workflows/merge.py`）：
   价值侧提供非策略张量、策略侧提供策略张量，按参数名前缀 `policy` 切分。
   两半必须来自同一条线（`rules_version` / `input_encoding` / `architecture` 一致，
   非策略张量的形状逐一相同），否则直接拒绝——接错了骨头在评测里表现为"结果看着正常、
   其实语义错位"。合并结果记 `merged_from`（两半的路径、`model_id`、`training_target`、
   `config_digest`）与 `training_target: "dual"`。

8. **首轮没有模型时用纯 MCTS 当教师**（走 C++ `generate`），有上一轮模型时用 NN 自对弈
   （走 `run_selfplay`）。两者产出的都是同一种数据批（ADR 0007 的来源记录一致），
   所以后面的步骤不需要知道区别——`steps/selfplay.json` 里用 `teacher` 字段记下是哪种。

9. **`generate` 的 stdout 末行是 `manifest.json` 的路径**（不是批次目录），
   批次目录取它的父目录。这条是 ADR 0008 的既有约定，脚本里曾经用 `tail -1 | dirname` 实现，
   现在写在代码里并校验文件确实存在。

## 理由

* **为什么坚持"薄"**：迭代的价值在于把**顺序**和**记忆**固定下来，而不是把每一步重新实现。
  任何一步出问题，用户仍然能用原来的 CLI（带 `--progress-json`、控制文件、`--continue`）
  去处理它——这是 P1/P2/P3 攒下来的东西，不该被一个新驱动废掉。
* **为什么标记文件而不是数据库/状态机**：一次迭代是目录 + 几个 JSON，人可以直接 `cat`、
  可以直接删一个标记来重跑那一步，不需要任何工具。这与 ADR 0020 的"清单是提交日志"同源。
* **为什么协议要统一注入**：ADR 0016/0018 已经证明"协议变量散落"是本项目最贵的错误形态
  （同一条曲线在不同协议下不可比，而差别只体现在哈希上）。迭代是最容易被塞进新旋钮的地方，
  所以在这一层就把协议固定成一份、写进产物。
* **为什么合并要有兼容性闸门**：两个 run 的产物看起来都是"一个完整模型"，
  形状与元数据都对得上并不代表它们来自同一条线。

## 替代方案

* **一条把四步串起来的 shell 脚本**（现状）：不可测、`tail -1` 抓路径、断在哪都要重跑。
* **把四步也做成配置文件**（用户已否）：跑谱/评测/评分的参数是"这一次动作"的属性。
* **把 iterate 做成一个长期运行的调度器**（带队列、并发、失败重试）：本项目的迭代是
  人工触发的实验循环，不是服务；现在引入调度器只会有没人读的配置。
* **合并时按形状推断哪一侧是策略路径**：前缀是既有的命名契约（`policy*`），
  推断会在结构变化时安静地选错。
* **首轮只支持 NN 自对弈（要求一个初始模型）**：那就需要一个"从零引导"的旁路，
  而纯 MCTS 教师正是 ADR 0013 用过的那条路，且几秒就能跑完。

## 验证方式

* **单元测试**（`python/tests/test_iterate_and_merge.py`，6 条）：合并按前缀取两半、
  不兼容的两半被拒（规则版本不同、形状不同）、`merge-halves` 的 CLI 接线与
  "stdout 末行是产物路径"；迭代的步骤标记幂等（预置标记 → 跳过且交回产物）、
  非法计划被拒（未知步骤、迭代内跑谱缺 `--samples`）、基线名字的解析（`random` / `mcts<数字>`）。
* **手工端到端**（本机 CPU，`--simulations 8 --lanes 8 --eval-games 20`，6.5 秒）：
  `iterate --name smoke --config train.yaml --samples 3000 --data-seed 12345` 四步全过——
  纯 MCTS-8 教师产出 3000 条 / 8 局 → 价值 run + 策略 run + 合并 →
  4 条臂（value / policy / nnmcts8 / random 基线）各 20 局 → 评分池新增 80 局并写出
  `rating.json`；stdout 末行是这一轮的完整模型路径。
  再跑一次同一命令：**四步全部跳过、0.0 秒**；`--steps evaluate,rate --force` 重评后
  评分池"新增 0 局"（去重生效），且逐局记录落在迭代目录里。
* **尚未验证**：
  1. 真正的多轮迭代（`--init-checkpoint` 指向上一轮的完整模型、NN 自对弈产出数据）——
     本次只跑了首轮形态（纯 MCTS 教师），`_step_selfplay` 的 NN 分支没有实测；
  2. 中断后从中间步骤续跑的实际场景（只测了"标记存在则跳过"这一半）；
  3. 评分池规模变大后的 `rating.json` 是否够用（现在只是把 `compute_ratings` 的结果
     重排一份；明细仍在 `rating` CLI 里）。
