# ADR 0025：推理精度的现状与暂不引入降精度开关

- 状态：已采纳
- 日期：2026-10-07

## 背景

架构迭代路线里有一项待决：要不要现在给 fp16/bf16 留接口。提出时的判断是"目前的小模型不足以
断言精度损失与性能提升"，并要研究"现在预留"与"后期再加"的成本差异。

研究分两步做完了：先查清接口现状（发现它其实已经预留了大部分），再在这台机器上把两个关键量
实测出来（吞吐 vs 批量、三种精度方案的叶级偏差）。结论是**不引入**，下面是依据与留下的口子。

## 决策

1. **暂不引入推理精度开关**：不给评测/自对弈路径接 autocast 或 `model.half()`，不加 CLI 与
   配置项。实测不支持它——真实批量下 bf16 反而更慢（0.88×），批量 4096 时也只有 1.19×；
   而叶级扰动是真实的（bf16 下 0.54% 的局面策略 argmax 会变），拿"没收益"换"要重定锚"不划算。

2. **协议字段 `inference_precision` 保留，并继续逐行记录**。它已经在用：NN 记录写
   `"float32"`、纯 C++ 记录写 `null`（池子里 460 + 400 条）。这是最便宜的一项预留
   （零成本、已在工作），保证将来开精度时**不需要数据迁移**，也不会与现有记录混比——
   协议系统会自动把它们分成两把尺子。

3. **不留空参数**：删掉 `BatchedEvaluator` 上那个未接线的 `dtype` 参数。它存在但从未参与
   计算（`self.dtype` 是死状态、两处构造都没传），谁按名字传 `dtype=torch.bfloat16` 都会
   **静默**拿到 fp32——比"没有这个参数"更糟。将来真要引入时，接线的成本是 15 行
   （一处 autocast + 复用 `--amp` 词表 + 把 dtype 名写进协议），与现在做没有差别。

4. **权重存储 dtype（真正的"量化模型"文件）不预留 metadata 字段，也不做转换工具**。
   `load_state_dict` 会**静默双向转换** dtype，所以"这份权重是不是量化过的"只能靠记录判断；
   但现存所有文件都是 fp32，"字段缺失 = float32" 对既有产物全部成立 → 以后加是零迁移
   （与 `head_width`/`groups` 那次同一模式）。导出与数值校验属于发布层，等精度结论出来再说。

5. **触发条件与顺序**（写下来是为了下次不必重推）：当**新架构让前向从延迟受限转为算力受限**
   时——更宽的网、更大的批量、加 attention 之后——按这个顺序走：
   ① 先按新结构重调 `lanes`/`in_flight`（批大小本身是吞吐的第一杠杆）；
   ② 同形状预热、用真实批量重测吞吐；若确有 ≥1.5× 收益，
   ③ 再用**配对设计**（同 checkpoint、同协议、同 seed，只改精度）+ ≥1600 局测能力损失；
   两者都过才引入（引入的代价是那条评分线要重新定锚）。

## 理由

* **延迟受限这个诊断是结论的关键**：fp32 的吞吐从批量 256 到 4096 涨了 6 倍多
  （24.1 万 → 153 万行/秒），说明每次调用的固定开销占主导；而降精度只减少算力时间，
  所以只在批量大到算力成为瓶颈时才见效。自对弈的真实批量（实测平均约 439 行/次）恰好
  落在**更慢**的那一段（0.88×）——这不是"收益小"，是**收益为负**。
* **叶级扰动不能只看价值**：bf16 的价值平均差 3.8 分看起来无害，但同一批测量里
  0.54% 的局面策略 argmax 变了。搜索的策略标签就是根访问分布，一次先验翻转会改变访问安排，
  再进到训练标签——这条传播路径正是 ADR 0017 记录的"批组成单独就能位移 +20.1 分"的同类效应，
  而 bf16 的扰动幅度比 fp32 的批序差（8e-7）大好几个数量级。
* **为什么现在与以后做成本几乎相同**：唯一会随时间变贵的是"记录"（协议字段与元数据），
  而协议字段已经在记录、权重 dtype 字段又满足"缺失即默认"的历史兼容条件，所以两侧都零迁移。
  剩下的接线工作量与时机无关。
* **为什么连"空参数"都要清掉**：文件里留一个静默空转的参数，等价于给下一个人挖一个坑；
  这次研究里它自己就是证据——研究的第一步差点被"接口看起来已经有了"误导。

## 替代方案

* **现在就接上 autocast（把接口做实）**：代码成本几乎相同（15 行）。不取的理由是没有证据支持，
  而且一旦有人真的开了，那条评分线就得重新定锚（每开一次精度多一把尺子）；
  在"网络变大"这个触发条件到来之前，它只会是被误用的旋钮。
* **现在就删掉协议里的 `inference_precision`**：省一格，但将来引入时已有记录会缺字段——
  按 ADR 0018 的原则"缺字段必须报错"，那批记录只能重跑。留着是零成本的。
* **现在就做 fp16 量化导出（推理版权重文件）**：多一种产物格式 + 一套固定棋盘数值校验，
  而收益在批量 4096 下也只有 1.19×（且 fp16 权重与 fp16 计算的叶级偏差几乎一样，
  说明"存"并没有额外的收益空间）。等触发条件到了再说。
* **INT8/INT4 量化**：在本项目的模型规模与批量范围内预期收益更小、校验成本更高，未评估。

## 验证方式

* **吞吐（RTX 5090，训过的 `c2-policy`，含编码，同形状预热 20 次、计时 200 次）**：

  | 批量 | fp32 | bf16 autocast | 加速 |
  |---|---:|---:|---:|
  | 256 | 24.1 万行/秒 | 22.6 万 | 0.94× |
  | 512 | 60.1 万 | 52.7 万 | 0.88× |
  | 1024 | 78.3 万 | 88.5 万 | 1.13× |
  | 4096 | 153 万 | 183 万 | 1.19× |

* **叶级偏差（2048 个局面，同 checkpoint，归一化价值单位 1.0 = 1024 分）**：
  bf16 autocast 价值平均差 ≈3.8 分（最大 29）、策略 argmax 改变 **0.54%**；
  fp16 autocast ≈0.46 分、argmax 不变；fp16 权重+计算 ≈0.6 分、argmax 0.15% 改变。
* **方法上的订正（留下以免重犯）**：必须用**同形状**预热。第一次在 4096 上量到 2.8×，
  那是只在 512 上预热 5 次就计时的假象——fp32 的 4096 形状第一次跑吃了冷启动。
* **代码侧检查**：`BatchedEvaluator` 不再有未接线的精度参数；`inference_precision` 只出现在
  协议清单、评测写出方与 C++ 的 `null` 声明三处。
* **尚未验证**：
  1. 更宽/更深的网与 attention 下的吞吐关系——**触发条件本身要重新测**（本 ADR 只记录
     "什么条件下该回来重测"，不预言那时的结论）；
  2. 真实自对弈的**端到端**加速（本次量的是纯前向 + 编码，不含 C++ 搜索与批组装的占比变化）；
  3. fp16 权重**文件**的加载路径（本次量的是内存里 `.half()` 的模型）；
  4. GPU 显存收益（本模型太小，不值得测）；CUDA 上 fp16 需要 loss scaling 的场景
     不在推理范围内，未涉及。
