# ADR 0027：推理管线的性能诊断与引擎优化方向

- 状态：已采纳（诊断、abandon 契约与并行化的实测结论）
- 日期：2026-10-07

## 背景

用户观察到自对弈时「显卡功率与 GPU 占用率不到 50%」，问是 benchmark 没做好、代码的性能释放
有问题，还是模型太小、时间浪费在调度与数据交换上。三个都要用测量回答，不能靠猜。

先排除掉的：

* **不是功耗/温度/显存墙**：功耗 275 W（上限 600 W）、温度 58 ℃、SM 时钟 2944/3090 MHz、
  显存带宽利用率 2.1%。同一张卡在紧循环里能稳定拉 578 W、占用 88–96%（下表）。
* **不是 benchmark 的问题，但 nvidia-smi 会低报**：`utilization.gpu` 按约 1 Hz 粒度判断
  "有没有核函数在跑"，在 2–3 ms 的小核函数之间会漏采样。用 CUDA event 量到的**真值**是
  **58.7%**，nvidia-smi 给的是 35%。
* **模型小确实是原因之一**：同一批量（1112 行）下，小模型（1.2M 参数）紧循环到 64.6%，
  换成 256 通道 / 39 块（48M 参数）就到 86.3%。每次调用的 GPU 工作只有 2.7 ms 时，
  编码/回传/启动开销占比就大。
* **但主因是单线程流水线**：整个自对弈进程 19 个线程里**只有 1 个在跑（100%）**，
  其余 18 个为 0%，16 核里 15 核闲着；代码侧对上了——`cpp/search/batched_engine.cpp`
  里没有任何线程结构，而纯 C++ 的 `generate` 用满了 `hardware_concurrency()` 个 worker。

## 诊断方法（已进生产代码，不是一次性脚本）

* `BatchedEvaluator` 按相位计时（编码 / 前向排队 / 取回），并用 **CUDA event** 单独量
  "GPU 真正执行了多久"——Python 侧的 `forward` 是异步的，墙钟量到的是排队而不是计算，
  唯一能说明 GPU 忙不忙的就是 event。
* `run_selfplay` 按轮计 `advance`（C++ 树搜索）/ `evaluate`（编码+前向+取回）/ `submit`（回填）
  三段墙钟，并把 `phase_summary()` 放进结构化进度与终态 `stats`。
  开销是每轮三次 `time.monotonic()`，可忽略；收益是"谁在等谁"从此有数可看。

实测（dt1 的双塔模型、256 模拟、lanes 64、in_flight 4、20 万条 / 479 秒 / 417 样本/秒）：

| 相位 | 秒 | 占墙钟 |
|---|---:|---:|
| `advance`（C++ 树搜索） | 76.9 | 16.1% |
| `evaluate` 合计 | 349.6 | 73.0% |
| — 编码 | 27.5 | 5.7% |
| — 前向**排队** | 238.9 | 49.9% |
| — 取回（含等 GPU 完成 + 拷回） | 81.3 | 17.0% |
| `submit`（C++ 回填） | 52.1 | 10.9% |
| **GPU 真正执行（CUDA event）** | **281.2** | **58.7%** |

结论：GPU 空出来的 41%（198 秒）几乎全是**同一个线程上的 CPU 工作**（树搜索 77 + 回填 52 +
编码 27.5 ≈ 157 秒，其余是 Python 与启动开销）。GPU 在等 CPU，而 CPU 只有一个线程。

## 决策

1. **把"补发在途请求"从 `advance()` 里挪出来，改成显式的 `abandon()`**。
   原先的自动补发是一个隐藏行为：advance 会把所有在途请求重新排队，这在"调用方总会把整批回填"
   的前提下是空操作，但它同时**堵死了管线重叠**——重叠要求"手上有一批没回填、同时继续 advance"，
   自动补发会把正在 GPU 上算的批次当成丢失的重复发一遍（重复 id 会让 `submit` 直接抛错）。
   现在契约是：**`advance` 交出去的一批，要么 `submit`，要么在确实丢了的时候显式 `abandon`**；
   异常路径（Ctrl-C 落在前向里、回调抛异常）由调用方调它——`run_selfplay` 的
   `except KeyboardInterrupt` 已经这么做了。

2. **把"为什么 GPU 会等"写进代码而不是留在对话里**：`phase_summary()` 随每次跑谱上报相位占比
   与 GPU 忙占比，任何一次跑谱都能看出流水线有没有退化。

3. **`in_flight_per_lane` 就是引擎的管线深度，这不是 bug 而是搜索语义的后果**。
   一条新测试（`engine_advance_waits_when_budget_is_full`）钉住这个事实：一次 advance 把每条
   lane 的在途预算用满之后，继续 advance 必须返回空批。**这条事实砍掉了"简单重叠"这条路**——
   想加深管线就得改 `in_flight`，而它是一个协议变量（ADR 0017 实测：单独改 lanes 就能让评分
   位移 +20.1 分）。

## 实测：三种并行/放大的路子，只有一条有效

诊断之后按"先量再改"把三种候选各测了一遍（都是同一批 64 条 lane、256 模拟）。
**判据用吞吐（模拟/秒），不用 GPU 利用率**——下面会看到利用率会把结论带偏。

**1）把 64 条 lane 分成 N 组、交错驱动**（A 组的批次在 GPU 上算时，CPU 推进 B 组；
不需要线程，靠 CUDA 的异步执行重叠）：

| 分组 | 模拟/秒 | 每次前向 | GPU 忙占比 |
|---|---:|---:|---:|
| 1 组 × 64 lanes | **150,479** | 569 行 | 58.6% |
| 2 组 × 32 | 111,921 | 298 行 | 68.4% |
| 4 组 × 16 | 67,355 | 147 行 | 75.5% |
| 8 组 × 8 | 36,422 | 70 行 | 78.8% |

GPU 占用一路涨、吞吐一路掉：分组让每次前向变小，而每次调用有一笔固定开销
（取回的同步与拷贝、编码、Python 胶水），小批量摊不掉。**否决。**

**2）提高 `in_flight_per_lane`**（同一条线程，只把每次前向做大）：

| in_flight | 模拟/秒 | 每次前向 | GPU 忙占比 | 缓存命中 |
|---|---:|---:|---:|---:|
| 4 | 150,495 | 1134 行 | 58.7% | 56.2% |
| 8 | 180,402 | 2188 行 | 47.4% | 55.4% |
| **16** | **196,245（+30%）** | 4113 行 | 42.3% | 53.9% |

**吞吐涨 30%，GPU 忙占比反而降了**：批量变大后每一行的核函数时间从约 2.5 µs 降到约 1 µs
（固定开销被摊薄），同样的活干的次数更少。**这条是有效的**，但它的代价写在搜索语义上：
在途模拟互相看不见对方 → 探索变浅，是协议参数。数据质量必须用一次完整迭代 + 评测判定。

**真实管线的复核**（同一批 1M 条、256 模拟、64 lanes，只改 in_flight）：
in_flight=4 时 417 样本/秒（首轮 dt2，跑到 43.8 万条时被杀），in_flight=16 时整轮平均
**747.5 样本/秒**（早期同一进度点上 592，即 +42%；整轮平均相对首轮 +79%），
批均值 1134 → 4055 行，显存带宽利用率 2.1% → 16.1%，功耗 275 → 299 W，
而 nvidia-smi 的利用率 35% → 33%（**又是那个假指标**：批量大了，活干得更省）。

**3）把 `advance` 的 lane 循环开线程**（本次实现的 `search_threads`，默认 1 = 与之前
逐字节相同）：在 in_flight=16 上测：

| 搜索线程 | 模拟/秒 | GPU 忙占比 |
|---|---:|---:|
| **1** | **197,707** | 41.8% |
| 2 | 172,271 | 36.5% |
| 4 | 154,393 | 32.7% |
| 8 | 136,714 | 30.6% |

**每加一倍线程就掉一截。** 原因具体且可修：每次叶子查找都要拿一次全局 `cache_mutex`，
而一条 lane 的一步搜索只有几微秒——锁争用吃掉了并行收益，附带把缓存命中率拉低（等于给
GPU 加活）。所以**否**：要让线程化值钱，得先把叶子缓存分片或无锁化，而分片本身会降低
命中率（命中率直接决定 GPU 的活量），是一笔需要单独测量的交易。

`search_threads` 因此**保留为默认 1 的实验钩子**（有测试守着"批大小与线程数无关、请求数守恒"），
并已进协议参数与数据来源身份：它改变调度，就不该悄悄和别的数据混在一起。

## 对"利用率低"这类判断的正确用法

利用率（`utilization.gpu`）低**本身**不是问题，但把它和"四项硬件资源都没满"放在一起看，
结论就很硬：CPU 多核只用 1/16、host 内存带宽差两个数量级、GPU 核函数时间占比 58.7%、
VRAM 带宽 2.1%——**四项都没到极限，说明时间花在"等"上，而不是花在"算"上**。
这正是 AGENTS.md 要杜绝的情形（应当并行的任务写成串行，让 CPU/GPU 干等）。
所以：**利用率是发现问题的手段，吞吐是判断改进的判据**——两者都要看，
只看后者会漏掉"靠摊销固定开销换来的假改进"。

## 结论与下一步

* **瓶颈的准确描述**：不是"GPU 没被用满"，而是**每次调用的固定开销 + 单线程搜索**让
  每个样本都要多付一笔钱。GPU 忙占比低是结果，不是原因。
* **当前可用的最好配置**：`in_flight_per_lane = 16`（+39% vs 4），代价是搜索语义变化
  → 必须用一次迭代 + 评测来判定数据质量是否可接受。这是唯一"改配置就能拿"的收益。
* **线程化暂不采用**：先要缓存分片/无锁，属于独立课题，收益上限也受命中率下降抵消。
* **模型变大不会解决它**：大模型让每次前向更长（利用率好看），但 CPU 每轮的活不变，
  真正的修法仍是"少付固定开销"或"把 CPU 的活并行掉"。

## 理由

* **为什么坚持"先量再改"**：这次诊断里有两个反直觉的结果——nvidia-smi 低报了 24 个点，
  而"把前向提前排一轮"这条看起来最自然的优化被 `in_flight` 的语义直接否定。没有相位分解，
  两个都会踩进去。
* **为什么补发要显式**：隐藏的自动补救会与"允许未回填就继续推进"互相矛盾，而两种行为都对
  各自的场景正确。显式之后，两者的边界由调用方掌握，而且异常路径不会静默变成重复请求。
* **为什么不直接上"多进程跑谱"**：每个进程会各写一批数据，批次语义（来源身份、局号、
  清单）会散掉；多进程能拿吞吐，但会把数据层搞乱，不值得。

## 替代方案

* **只调 nvidia-smi 的采样频率/用别的工具**：不改代码，但那只是把数字看清楚，不解决等 CPU 的问题。
* **torch.compile / CUDA graph 降启动开销**：前向排队 239 秒里有一部分是核函数启动；
  但训练侧实测 `torch.compile` 是负收益（慢 28 倍），推理侧未测，且它改变数值（属协议级变量）。
* **把编码也搬到 C++/融合进前向**：编码只占 5.7%，不值当。
* **接受现状**（数据质量优先，慢就慢）：在"发现问题解决问题"阶段不取——这是结构性浪费。

## 验证方式

* **复现诊断的命令**（不需要 GPU 采样工具）：跑一小段自对弈，读 `stats["phases"]`：
  `advance/evaluate/submit` 占比、`gpu_busy_rate`。本次基线：**gpu_busy_rate = 0.587**、
  `advance_share ≈ 0.16`、`submit_share ≈ 0.11`。
* **紧循环上界**（表见 BUILD.md 的性能一节）：小模型 1112 行 64.6% / 5120 行 81.7% /
  16384 行 88.1%；大模型 1112 行 86.3%。
* **契约测试**：`engine_abandon_requeues_dropped_batch`（显式放弃之后仍能跑完、请求数守恒）、
  `engine_advance_waits_when_budget_is_full`（预算满 ⇒ 空批、未回填不重复发、回填后立刻能推进）。
* **尚未验证**：`in_flight` 提高后的数据质量（需要一次完整迭代 + 评测才能判定——
  这是下一步，也是唯一还没被数据回答的问题）；缓存分片/无锁化之后的线程化收益
  （本次只证明"在现有缓存设计下不划算"）。
