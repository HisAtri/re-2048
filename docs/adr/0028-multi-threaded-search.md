# ADR 0028：多线程搜索（K 个引擎共享写入侧 + 合并推理线程）

- 状态：已采纳（实现与实测；**已知未达到上限，缩容方案见"下一步"**）
- 日期：2026-10-07

## 背景

ADR 0027 的诊断结论是：GPU 空出来的时间几乎全是**单线程上的 CPU 工作**（树搜索 27%、
编码与胶水约 14%），而四项硬件资源（CPU 多核、host 内存带宽、GPU 算力、VRAM 带宽）一个都
没到极限。用户据此指出：跑谱本来就是可并行的，四项都没满就意味着代码在串行。

同一份 ADR 也记下了两条被实测否掉的路：

* **在一个引擎内部并行推进 lane**：每次叶子查找都要拿全局 `cache_mutex`，而一步搜索只有
  几微秒 → 线程越多越慢（197k → 172k → 154k → 137k 模拟/秒）。
* **把 lane 分成多组交错驱动**（靠 CUDA 异步重叠，不开线程）：分组让每次前向变小
  （569 → 70 行），每次调用的固定开销摊不掉 → 吞吐一路掉（150k → 36k）。

用户的要求很明确：**优先在程序内开线程做任务分配**，但**不要**真开多个跑谱进程各建一批数据
（"这样很乱"）。

## 决策

1. **K 个搜索引擎，各自持有叶子缓存**。锁争用从根上消失（每个引擎的缓存只被它自己的线程
   访问），而 lane 之间本来就是独立的。

2. **共享一个写入侧**（`SampleSink`，`cpp/dataio/sample_sink.h`）：分片缓冲、按局号顺序落盘、
   样本目标、终态清单、续跑校验、停车广播。局号从共享的原子计数取，落盘顺序由局号决定，
   与调度无关——所以 K 个引擎产出的仍是**一批**数据：一个批次号、一份清单、一套连续局号。
   第 N 局的内容只由 (种子, 局号) 决定（ADR 0007/0020），因此 K 个引擎**共用同一个种子**即可，
   不需要编造 K 个种子（批次的身份仍然准确）。

3. **一个合并推理线程**：它把各组此刻就绪的请求**合并成一次前向**再分发结果，批量因此不会
   因为分组而缩水（这正是"分组交错"失败的原因）。GPU 上只有一个前向在跑，这是硬件的形状。

4. **重叠来自 GIL 释放**：搜索线程调用 `advance()` 时 C++ 会释放 GIL（绑定里早就这么写了），
   所以 K 个线程的搜索在不同核上真并行；推理线程在 GPU 上算这一轮时，别的搜索线程已经又推进了。

5. **默认 1 线程 = 与从前逐字节相同**：`search_threads` 同时是 Python 侧的引擎数与协议参数
   （它改变调度与批组成，ADR 0017），所以自己一版数据、自己的来源身份。

6. **引擎内部不再并行推进 lane**：那份代码删掉，并在注释里留下原因与实测数据（避免后人
   重新发明同一条死路）。

## 实测：有效，但只拿到 1.2×

同一批 64 lanes / 256 模拟 / in_flight=16，只改搜索线程数（口径＝各引擎模拟数之和 / 墙钟）：

| 搜索线程 | 模拟/秒 | 相对 | 每次前向 | GPU 忙占比 | 搜索线程忙占比 | 缓存命中 |
|---:|---:|---:|---:|---:|---:|---:|
| 1（顺序驱动） | 182,256 | 1.00× | 2511 行 | 45.8% | 20.8% | 56.5% |
| 2 | 204,185 | 1.12× | 1426 行 | 61.0% | 14.7% | 59.1% |
| 4 | 190,445 | 1.04× | 1473 行 | 60.9% | 6.4% | 60.7% |
| 8 | **218,023** | **1.20×** | 1740 行 | 54.6% | 3.9% | 61.6% |

**重叠确实生效**（GPU 忙 45.8% → 61%），**但每次前向的批量掉了一半多**（2511 → 1426-1740 行），
而搜索线程大部分时间在等（忙占比 20.8% → 3.9%）。原因是结构性的：各引擎是**错峰**的
（一个在等答案时另一个才产出），推理线程只能合并"此刻就绪"的那点请求。

**两个杠杆在这里互相打架**，这是本轮最重要的发现：

* 重叠想要"更多、更小的并发批"（CPU 在批算出前得有事可做，而在途预算是有限的）；
* 效率想要"更少、更大的批"（每次调用的固定开销只能靠批量摊薄，ADR 0027 实测 1112 行 64.6%
  vs 16384 行 88.1%）。

## 下一步（已知的缩容方案，尚未实现）

**让 `advance` 每次只发放一部分在途预算**（例如 `in_flight_per_lane / 2`）：于是每个引擎在
自己那批算完之前**总是还有可推进的余量**，搜索线程不再空等，推理线程也能把 K 个引擎的请求
真正合并成一个大批——两个杠杆同时满足。代价是在途集合的**平均**规模变小（搜索看到的备份更少），
属协议参数，必须记录并用评测确认。

预期收益：GPU 忙占比向 80–90% 走，吞吐 1.5–1.8×。这条留给下一次改动，本轮先用已验证的
1.2× 跑一轮数据（dt3）。

## 补充实测（多进程，2026-10-07）：真正的限速器是 CPU 的线程池过度订阅

用户要求"先开 4 个或 8 个进程，它理应真正触碰到 CPU/GPU/RAM/VRAM 其中一项瓶颈"。
做了（每进程 64 lanes / in_flight 16 / 256 模拟 / 各自 seed 与输出目录）：

| 配置 | 总 CPU | GPU 利用率 | 功耗 | VRAM | 进程 RAM |
|---|---:|---:|---:|---:|---:|
| 1 进程（默认） | 37% | 35.7% | 297 W | — | — |
| 1 进程 + `OMP_NUM_THREADS=1` | — | 38.0% | 318 W | — | — |
| 4 进程（默认） | **98.7%** | 57.5% | 443 W | 10.2 G | 4.6 G |
| **4 进程 + 线程=1** | 25.5% | **83.8%** | 586 W | 10.1 G | 4.7 G |
| **8 进程 + 线程=1** | 50.8% | **91.0%** | **598 W** | 13.6 G | 9.3 G |

三条结论：

1. **单进程无论如何都被钉在 ~38% GPU**——`advance → 前向 → 回填`严格串行，这是本文档前半部分
   诊断的那个上限；本 ADR 的 K 引擎 + 合并推理线程把占空比从 45.8% 提到 61%（+29%），
   但它抬不过"单进程一次只有一个前向在飞"这条天花板。
2. **多进程能爬到真正的资源极限**：8 进程时 GPU 91%、功耗 598 W（上限 600 W），
   CPU 8/16 核、RAM 9.3/30 GiB、VRAM 13.6/32 GB 都远未到顶 → **瓶颈是 GPU 的功耗/时钟**。
3. **拦住多进程的是代码，而且是一行配置级的**：torch 的 CPU 侧算子默认按核数开 intra-op
   线程池，而这条流水线里 CPU 算子全是极小的（uint8→int64、输出拷贝），真正的算力在 GPU 上。
   4 进程就是 64 个线程抢 16 核 → CPU 98.7%、GPU 只剩 57.5%；**每个进程钉成 1 线程之后
   CPU 降到 25.5%、GPU 升到 83.8%、功耗 443 → 586 W**。已固化进代码：
   `runtime/selfplay.pin_cpu_threads()`（`run_selfplay` 与 `run_evaluation` 入口各调一次）。

这同时订正了本 ADR 前半部分的自我判断：当时把"多进程会各建一批数据"当成不可接受（用户也这么
认为），于是走了进程内 K 引擎这条路。实测下来多进程才是拿到资源极限的形态，而"多批次"这件事
本来就被多来源训练吃下了（ADR 0021）——**进程内 K 引擎的价值退化为"单进程内的 +29%"，
不再是主线**；它的默认值 1 也保证了既有行为不变。

## 替代方案

* **一个引擎内并行 lane**（已实现过）：实测负收益，见背景。
* **多进程跑谱**（每个进程一套输出）：用户明确否掉——批次会散，数据层会被搞乱。
* **共享叶子缓存 + 原子操作（无锁哈希）**：能去掉锁但不解决"一个引擎的 lane 一轮就用满预算"
  这条边界，因此无法带来重叠；而分片缓存会降低命中率（命中率直接决定 GPU 的活量）。
* **CUDA 图 / 融合编码降每次调用的固定开销**：编码只占 5.7%，不值得。
* **K 个引擎各写自己那一批**：数据会被切成 K 份，来源身份、局号、清单全部要重做。

## 验证方式

* **C++**（`cpp/tests/test_engine.cpp::engine_two_engines_share_one_sink`）：两个引擎共享一个
  sink → 都跑到收尾、共享样本数恰好等于目标、清单里样本数与局数正确、分片序号连续无空洞、
  `workers` 与协议参数 `lanes` 记的是**整批**的值（8）而不是单个引擎的（4）、
  `search_threads` 如实记录、收尾幂等且收尾后写入侧处于停车态。
* **Python**：`python/tests`（58 条）全绿；`search_threads=1` 时走原顺序驱动，行为不变。
* **实测（引擎级）**：上表（4 档线程数，30 万样本 × 4）。
* **实测（整轮）**：dt3 = 256 模拟 / in_flight=16 / 8 线程 / 100 万条 → 整轮平均
  **964.7 样本/秒**（dt2 = 同参数但单线程：747.5）＝ **+29%**，批均值 3323 行。
  两个数字的差（引擎级 +20% vs 整轮 +29%）来自批次分布：长跑里各引擎更容易凑到同步，
  合并出的批次比 30 万样本的短跑大（3333 行 vs 探针里的 1426-1740 行）。
* **训练与棋力（同一锚点 mcts256）**：dt3 的**离线指标全面更好**
  （策略一致率 43.0% → 49.5%、CE 1.1847 → 1.1340、候选命中 53.4% → 55.6%），
  但 **NN-MCTS-256 的评分反而低 44 点**（944.6 → 900.5，各 ±23，≈2σ；均分 18976 → 17464）。
  也就是说：这一轮训出的模型**离线更拟合、搜索更弱**——正是 ADR 0013 记下的自举退化，
  与引擎无关。**诚实的不确定**：dt3 的数据由 8 线程自对弈产出（调度与批组成变了，ADR 0017），
  所以这 44 点里有多少是"自举退化"、多少是"数据调度变了"，单跑一次分不开；要分开得用
  同线程数的对照或配对设计（ADR 0014：20 点级差异需要 ≥1600 局或多 seed）。
* **尚未验证**：缩容方案（`advance` 只发放部分预算）的收益；多线程下长时间运行的稳定性
  （本轮只跑了 30 万样本 × 4 档 + dt3 整轮）；`lanes` 不能被线程数整除时的取整行为
  （代码里是 `lanes // threads` 再乘回去，会**减少**总 lane 数——目前只在能被整除时使用）。
