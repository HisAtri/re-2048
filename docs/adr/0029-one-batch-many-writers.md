# ADR 0029：一个数据批、多个写者（跨进程并发跑谱）

- 状态：已采纳
- 日期：2026-10-07

## 背景

多进程跑谱是拿到资源极限的形态（ADR 0028 实测：8 进程 GPU 91%、功耗 598/600 W，
而单进程被钉在 ~38%）。但每个进程各建一个批次目录，于是"一次运行"变成 N 个数据集，
训练侧要去列 N 个来源——**反直觉，而且给训练添麻烦**。

用户的质疑切中要点：**数据写入本身没有顺序要求**。核实下来确实如此：每条记录自带局号
（`RECORD_DTYPE` 的 `episode`），每个分片自带局号区间，读取端从不靠"文件里的位置"推断局号。
真正强制有序的只有三处实现细节：`add_episode` 把"已写局数"当"下一个局号"、`resume` 用
`manifest.episodes` 接着编号、`verify` 假设"清单顺序 = 局号顺序"。三处都可改。

## 决策

1. **局号由跨进程发号器发放**（`EpisodeCounter`，`<批次目录>/episodes.counter` + flock）：
   每次领一块（4096）在进程内顺序发完再领下一块——把"每局抢一次锁"变成"每几千局抢一次锁"。
   **号必须从中心发**：一局的内容由 `(种子, 局号)` 决定（ADR 0007/0020），各写者自己编号会让
   同一 seed 下不同写者造出同一局。

2. **每个写者写自己的分片文件**，文件名带写者标识（pid + 启动时刻），不可能撞名
   （撞名 = 覆盖别人的分片 = 丢数据）。

3. **清单在文件锁下读-改-写地合并**（`manifest.lock` 的 flock，不用锁 manifest 本身——它会被
   原子替换）。不加锁就会互相覆盖：覆盖等于把别的写者已提交的分片从清单里抹掉，数据还在盘上
   但读取端永远看不到。

4. **分片声明"局数"与"局号跨度"两个字段，跨度重叠合法**。同一写者的多局完赛顺序不定，
   一个分片的 `[first, last]` 只是**跨度**，不是它拥有的集合；"整批局数"只能按各片记录的
   局数求和，不能用区间长度、也不能用最高局号推。

5. **顺序续跑（`resume`）保留逐字节复现**（ADR 0020 的强判据）：把发号器**重置**到"已有的
   最大局号 + 1"——块预留会让号跳到 4096，不重置就再也不是同一批数据了。此时是单写者，
   重置安全。**`join` 绝不重置**（别的写者可能正握着预留的号）。

6. **并发创建天然幂等**：发号器文件不存在时才初始化；`--join` 指向空目录等价于"新起一批"。
   实测四个进程同时起跑时，"每个都重置发号器"让局号重叠约 4 倍——这是被独立核验抓到的。

7. **一个 `stop` 停整批**：join 时控制文件**粘住**（不删）。一次性消费只能停住抢到它的那一个
   进程，其余会继续跑——那不是用户按 `stop` 时的意图。

8. **作业目录按进程分**（`runs/<批次号>-p<pid>`），批次数据仍是一个目录。多个进程共用一个
   作业目录会互相踩 `status.json.tmp`（实测直接崩掉两个进程）。

9. **`verify` 的职责收窄**（用户问"它的目的到底是什么、是否可以放弃"）：留下**只有它能做**的
   两件事——分片摘要（数据在盘上躺久了有没有被改过）与 `--replay`（用 `(seed, 参数)` 重推一遍
   对哈希，证明"这批数据真的由它声称的协议产出"，而不是清单里的 provenance 被人改过）——
   外加便宜的条数账。**删掉一切编码了布局假设的检查**：局号连续递增、清单末片就是末局、
   只有末片可以不满、区间不重叠。它们在多写者下不再是不变量，而结构正确性另有更上游的保证：
   原子落盘（tmp+rename，带 pid 的 tmp 名）保证分片非整即无、清单在文件锁下改、写者自己查
   片内重复、读取端加载时也校验版本与条数。**同类经验**：这两轮里我三次被"把实现细节当成
   不变量"咬到，删掉比补上更对。

## 理由

* **为什么号从中心发而写入顺序不管**：前者是语义（一局的身份），后者只是落盘策略。
  分开之后，"顺序"这条约束从数据层消失，多写者才成为可能。
* **为什么要锚定"逐字节复现"**：它是这套数据唯一能自证的判据（ADR 0020）。凡是让它失效的
  设计（块预留导致续跑换号）都必须被显式处理掉，而不是"接受差异"。
* **为什么 verify 要减而不是加**：它此前承担了太多"结构一定对"的断言，而那些断言依赖写入侧
  的布局选择；写入侧一改（多写者），它们就从保护变成阻碍。留在里的必须是与布局无关的判据。

## 替代方案

* **每个进程各写一批，训练侧列 N 个来源**：用户已否（反直觉、给训练添麻烦）。
* **单写者 + 队列（各进程把样本发给一个写者进程）**：多一层进程、多一份复制与故障面，
  而写入本身并不需要中心化——只有发号需要。
* **放弃 verify**：可以省掉一个工具，但会丢掉两条与布局无关、别的路径给不出的判据
  （摘要、重放）。收窄后它很小，保留成本低。
* **给清单加"每片局号集合的摘要"以便校验唯一性**：为了一个写入侧结构上已排除的问题
  （发号器保证不重号）付额外的复杂度，不值。

## 验证方式

* **端到端（4 进程 join 同一批，实跑）**：一个批次目录、一份清单、**4 个写者**的分片、
  496,534 条 / 500 局 / 25 个分片；独立核验"局号重复 0 个、不同局号 500 个 = 清单局数、
  记录总数 = 清单样本数"；**`verify` 通过（`ok: true`，无问题）**；
  GPU **85.0%**、功耗 **594 W**（上限 600 W）、显存 10.4 GB。
* **C++ 测试**：`dataio_pause_resume_matches_oneshot`（顺序续跑与一次跑完**逐片哈希相同**——
  这条强判据在改动后仍然通过）、`dataio_resume_refuses_other_source`、清单往返（含
  `episodes`/`next_episode` 两个新字段）、`engine_two_engines_share_one_sink`（同进程内多引擎
  共享写入侧）、`engine_abandon_requeues_dropped_batch` 等，共 30 项全通过。
* **尚未验证**：8 进程 join（只测了 4）；控制文件粘住后"一条 stop 停整批"的实际效果
  （本轮用 SIGINT 逐个停的）；跨机器/NFS 上 flock 的语义（本地文件系统成立）。

## 后续订正（2026-10-08）：`--samples` 目标改为**按整批**判定（已实现）

**问题**：4 进程 `--join`、`--samples 1000000` 实测产出 **4,000,000 条 / 2,858 局**——
每个进程各跑满 100 万。原因在写入侧：`SampleSink::target_reached_locked()` 比的是
`writer_->samples_written()`，而它是 `flushed_samples_ + buffered_samples()`，**只算本进程**。
同进程内多引擎共用一个 writer 时口径是对的（那条 C++ 测试也据此通过），跨进程就各算各的；
这与 CLI 写的"续跑时是**整个批次的累计**目标"相反。

**改法**：让目标判定读**批级统计**——批级总量就是清单里各分片之和（本写者的那部分已在里面），
加上本写者还没落盘的缓冲（`ShardWriter::batch_samples_written()`）。清单在文件锁下读，
所以刷新**节流到 250ms**；每次合并清单时顺手更新，省掉一次读。

* **进程数随便改**：不再需要"目标 ÷ 进程数"这种配额分摊，也没有任务分配平衡问题——
  局号由共享发号器动态发放，目标由整批统计判定，每个进程看到同一个数。
* **join 模式下达标时不再截断末局**：多进程下"该截哪一局"没有唯一答案；而且数据集不需要
  精确规模。单写者路径的行为**一字未改**（那里截断能让总数恰好等于目标，且单写者下
  "批级"与"本进程"本就是同一个数）。
* **超出量的量级是"在途的局"**：达标后正在进行的局必须走完（否则局号会出现空洞），
  所以实际总量 ≈ 目标 + 进程数 × lane 数 × 每局样本数。实测：2 进程 / 目标 6 万 → 63,169
  （+5.3%）；目标越大相对偏差越小。这条语义写进了 CLI 帮助。
* **进度也按整批报**：以前 4 个进程各报各的（33%、91%…），批级已经 360 万条时看不出来。
* **测试**：`python/tests/test_selfplay.py::test_join_samples_target_is_batch_level`
  ——起 2 个真进程 join，断言总量落在 [目标, 目标 × 1.4] 内（旧实现会接近 2× 目标，
  这条上界正是用来把两种语义分开的）。
* **连带的语义订正**：目标是"**至少**这么多"，不是"恰好"。`verify` 里"完成的批样本数
  必须等于目标"因此改成"必须 ≥ 目标"——单写者路径仍然会截断末局命中恰好等于目标，
  但那是**做到**的性质，不是能当不变式来验的东西。实测两个 join 批（6 万目标 → 63,169、
  不限量 + 外部 stop → 54,147 后 `--continue` 收尾）都能通过校验。

**仍未做**：从编排（`iterate`）一键起 N 个 join 进程——目前要并行跑谱得手工起 N 条命令。
样本目标这条障碍已经拆掉，剩下的只是启动便利。
