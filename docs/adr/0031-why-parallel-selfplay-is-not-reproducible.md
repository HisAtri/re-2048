# ADR 0031：并行跑谱不可复现的原因不是缓存，是"挂起不回填"

- 状态：已采纳（诊断 + 分界线实测）；**处置已定：训练数据的产出只用 `--join` 多进程，
  `--search-threads > 1` 只用于吞吐实验**（代码里已加启动警告与 CLI 说明）
- 日期：2026-10-08

## 背景

发现多线程跑谱（`--search-threads 8`）两次运行产出**不同的棋**后，问题从"能不能复现"
转成"为什么不能"。直觉上（也符合 KataGo 的形态）：缓存只是省掉一次前向，命中与未命中
应当给出同一个值，因此"横向拓展"不该影响 MCTS 的行为。下面把这条直觉对在哪、错在哪分开。

## 缓存实现（读代码得到的事实）

* **两层结构**（`cpp/search/batched_engine.cpp:151-266`）：
  * 定长**开放寻址表**（线性探测，`kProbeLimit` 个槽），槽位只会从"空"变"占用"、从不被
    清空，容量（默认 2^17）远大于工作集（数百个在途局面），所以几乎不发生驱逐。
    键 = `(board, kind)`，索引取乘法混合哈希的高位。**不是** 2 路组相联——那种结构下
    几个高频局面互相驱逐会造成活锁（实测踩过：2577 个局面里 3 个高频局面撞进同一 set）。
  * `fresh_answers`：本轮刚回填的答案放在一张**不参与驱逐**的小表里，只在整个 `advance`
    期间有效。它存在的唯一理由是保证"一个决策节点要同时命中策略 + 最多 4 个 afterstate
    价值"能凑齐，否则进度依赖缓存容量。
* `cache_get` **没有副作用**，命中返回的就是那次前向的结果。ADR 0017 另外实测过：
  **批内位置不影响结果**（同一局面重复 320 份，value 逐位相同；整批循环移位后回到位置 0，
  logits 差恰好 0）。

⇒ **"命中缓存 = 跳过 GPU，不改变行为"这条直觉，对缓存本身是对的。** 缓存不是数值说谎者。

## 真正的原因：挂起不回填（在途模拟的半计价树）

一条模拟在 `start_simulation` 里沿路径把 `edge_visits[action]` 自增，`edge_q_sum` 却要等
回填才更新。若叶子需要神经网络计算，这条模拟挂进 `lane.pending` **而不回填**
（`batched_engine.cpp:777-831`，在途上限 `lane.pending.size() >= in_flight_per_lane` 处停手）。
于是在途的模拟看到的是"半计价"的树：在途子节点的 Q 被低估，探索项用的 `node.visits` 也滞后。

**关键在于：一次模拟会不会挂起，取决于缓存里是否已有该 (board, kind)。** 命中就在
`start_simulation` 内直接完成，根本不进在途。缓存跨 lane 共享、命中与淘汰取决于全局工作集，
于是 `lanes` / `in_flight` / `cache_entries` / 交付时序共同决定了每个决策步的
（选择 → 展开 → 回填）序列——**这就是"横向拓展影响 MCTS 行为"的通道，它不在算子层。**

ADR 0017 的四条对照把它钉死了（此处只引结论，推导见该 ADR）：

| 对照 | 结果 |
|---|---|
| 同 seed 只改 `lanes` 8→16（GPU） | 16 局里 1 局逐局一致 |
| 同上，**CPU**（浮点噪声小四个数量级） | 仍是 1/16 ⇒ **排除浮点通道** |
| `in_flight=1`（彻底结算再开下一条），`lanes` 8→16 | GPU 与 CPU 都 **16/16** 一致 |
| `in_flight=1`，缓存容量 131072 vs 1024 | **16/16** 一致（均分都恰好 13102.0） |
| `in_flight=4`，缓存容量 131072 vs 1024 | **0/16** 一致 |

最后两行是全部证据里最干净的：**在途为 1 时缓存无论如何都不影响结果；在途 > 1 时缓存影响每一局。**
⇒ 通道是"挂起造成的统计滞后"，不是缓存给出的值。

放大机制：根节点取的是**整数**访问数的 argmax，顶层两方向一旦被这点差异换序选招就翻转；
而随机块来自 `derive_seed(seed, kSaltEnvironment, episode, step + 1, 0)`，按 (局号, 步号)
派生、**与轨迹无关**，所以翻转一步 = 同一串随机数落到另一个棋盘 = 余下整局分叉。

## 那为什么单线程能复现、多线程不能？

* **单引擎单线程**：驱动节奏固定（advance → 前向 → submit 整批），每条 lane 的"挂起/回填
  时间线"由配置唯一决定。实测：同配置两次运行 **27/27 局逐字节相同**。
* **K 引擎共享一个合并推理线程**（ADR 0028）：一个 lane 的分组交付取决于"此刻队列里有什么"，
  即时序决定；不同运行的分组不同 ⇒ 挂起与回填的时序不同 ⇒ 不同棋。实测（同模型、同 seed、
  同其它参数，两次 8 线程运行）：共同局 11 个里只有 **2 个**长度相同，而**局号相同**的局
  长度是 973 条 vs 475 条——同一局号下了两盘完全不同的棋。
* **多进程 `--join`（每进程单线程，共享发号器与写入侧）**：可复现。实测两次运行
  **52/52 局逐条相同**。原因是每进程的节奏仍是固定的，局号→内容的映射不受"哪个进程拿到它"影响。

**分界线因此是：一个进程内是否只有一个推进节奏。** 这与 ADR 0028 决策 2 的前提
（"第 N 局的内容只由 (种子, 局号) 决定，因此 K 个引擎共用同一个种子即可"）冲突：该前提
只在单线程时成立；K > 1 时内容还依赖调度，且**由 (种子, 局号) 无法重建**。

## 附带发现（同一次检查里撞到的）

1. **批大小确实会扰动浮点**，但量级小、且是阶跃：同一块棋盘放进批 5 与批 320，
   `value` 最大差 5.8e-4（归一化），cuDNN 按批大小切换内核。今天的实测
   （批 1 vs 批 ≥3：logits 最大差 1.2e-3 = 1.18 原始分；**同一批大小重复前向逐位相同**）
   与之一致。ADR 0017 的 CPU 对照已把它排除为主通道，它只是第二位扰动。
2. **`verify` 的重放不覆盖自对弈数据**：重放走 `run_generate` → `make_selector(policy)`
   （`cpp/program/episode.cpp:129-138`），而该工厂只认 `random` / `mcts`；`policy=nn` 的批次
   会以"重放失败: 未知策略: nn"收场。所以"重放会使用与生成时不同的线程数，因此验证了数据
   与线程数无关"这句话目前只对纯 C++ 路径成立。
3. **三个 dt 批连读都读不了**：当前读者要求分片级 `episodes` 字段（ADR 0029 引入），而
   dt1/dt2/dt3 的清单是在那次改动之前写的，`verify` 直接报"清单读取失败: JSON 对象缺少键:
   episodes"。字段是**强制**的、`schema_version` 没有跟着变，所以旧清单被判为不可读
   （拒绝而不是猜——方向是对的，代价是这三个批的数据要重新产出）。

## 下一步（处置方案）

1. **训练数据的产出只用可复现路径**：`--join` 多进程（每进程单线程）。`--search-threads > 1`
   只用于吞吐实验，产出的数据不入训练线——因为它连"这批数据是什么"都无法确认（重放不了）。
2. 若确实想用 K 引擎跑谱并保持可复现，正确的修法是**让挂起结构不再依赖时序**，两条路：
   * **按轮原子交付**：一条 lane 的一轮请求（它的整批在途）作为单位交付，缺项就缓冲等待，
     等齐再结算。代价：合并批次会变小（lane 自己在等待时本来也不干活）。
   * **给在途模拟计入虚拟损失**（KataGo 式），让"挂起"不再是一种隐藏的状态差异。
     但即使如此，交付顺序仍影响"何时计入"，所以还要配合轮原子交付才能逐位可复现。
3. `--search-threads` 与 `--join` 在**语义上不等价**这件事，应当写进 CLI 帮助与 ADR 0028 的
   状态说明：前者是吞吐旋钮（数据不可复现），后者是并行路径（数据可复现）。

## 验证方式

* **单线程可复现**：同配置两次运行，27/27 局逐字节相同。
* **多线程不可复现**：共同局 11 个里只有 2 个长度相同；同局号 973 条 vs 475 条。
* **多进程可复现**：`--join` 两进程两次运行，52/52 局逐条相同。
* **缓存不是原因**：`cache_get` 无副作用；批内位置不影响结果（ADR 0017）；
  `in_flight=1` 时改缓存容量结果 16/16 不变（ADR 0017）。
* **通道是在途挂起**：`in_flight=4` + 改缓存容量 → 0/16（ADR 0017）。
* **浮点是第二位**：批大小改变 logits 1.2e-3（1.18 原始分）；同批大小逐位可复现；
  CPU 对照 1/16（ADR 0017）排除其为主因。
* **尚未验证**：轮原子交付 / 虚拟损失能否在 K > 1 下恢复逐位可复现（未实现）。
