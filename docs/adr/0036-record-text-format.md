# ADR 0036：棋谱文本格式

- 状态：已采纳
- 日期：2026-10-08

## 背景

WebUI 要做复盘与导入导出，而仓库里至今**没有任何棋谱格式**：训练数据是定长记录
（ADR 0007，192 字节样本），评测 JSONL 是逐局汇总（分数/步数/协议），两者都不含走子
序列或盘面序列。盘面编辑器要造局面、复盘页要回放、会话要落盘，三处都需要同一种记录。

这个格式要同时服务三件事：**人可读可手写**、**GUI 与后端按单条命令交互**、
**可被独立重放**。第三条是这个项目的一贯要求（`verify` 靠重放比对守住数据可信）。

## 决策

1. **GTP 风格文本，一行一条命令**：`clear` / `set <值> <坐标>` / `move <方向>`。
   命令行内**不做括号或逗号列表**——一行一命令才能增量追加（活棋局每步追加一行）、
   可 diff、报错能指到具体行。多块初始化就是多行 `set`。
2. **文件头带版本**：`record_format <n>` 与 `rules_version <n>`，缺失或不匹配**直接拒收**。
   `#` 起首为注释行。
3. **生成块写成显式 `set`**：棋谱因此**不含随机性**——重放不需要种子、不需要 PRNG、
   不需要复现引擎的随机流。这是选文本格式最主要的收益，也是下面两条的前提。
4. **坐标**：`a1` 为左上角，字母是列（左→右 `a..d`），数字是行（上→下 `1..4`）。
   与 GTP 的行序（自下而上）相反，所以必须写进规范而不是留给约定。前端棋盘显示坐标。
5. **值域是键表**：`null` + 2^1…2^17 共 18 个键，查表校验。不用"是不是 2 的幂"的
   计算式校验：值空间本就有限且可枚举，表既不更弱，又天然可扩展（追加键 + 抬
   `record_format`，正好用上第 2 条）。面值与本项目内部的指数（ADR 0005）之间的转换
   只在本格式的编解码处存在一处；**`probe --board` 吃的是指数，两者不同**，文档写明。
6. **上限 2^17，越界显式拒绝**：4×4 的理论上界就是 2^17（ADR 0005 已写明这个数），
   超出它的值不会从任何真实棋盘推出来。两个 2^17 合并得到 2^18 是唯一能越界的路径，
   拒绝它之后键表在编辑器的一切操作下**闭合**，"记录里的值只可能是键表成员"于是成为
   一条结构性质，而不是靠事后检查维持。
7. **解析与应用分两层**：parser 只认语法与键表（**不持棋盘、不判规则**）；applier 把命令
   作用到棋盘上（`move` 走 C++ 的 `apply_move`，规则权威仍在那一处）。**应用不了就失败
   退出，绝不静默跳过**——静默跳过的记录，读起来和走出来的会是两盘不同的棋。
8. **首版只存对局记录**：不存分数（每次 `move` 的合并分可推导，存了就有两个事实源，
   迟早不一致）、不含分析标注。`clear` 把棋盘复位到空；初态本来就是空，所以不强制它
   必须出现在第一条，也就不引入"第一条必须是什么"这类结构规则。
9. **不做合规性校验、不做严格模式**：不检查"每个 `move` 之后恰好一个生成块"。
   这类判据会与第 7 条的局部性冲突，而且手工摆的题目局面、导入的残局本来就不该有生成块。

## 理由

* **为什么是文本而不是二进制**：对局记录的量级是每局数百行，解析不可能成为瓶颈；换来的是
  可手写、可 diff、可贴进 issue、可被任何人独立重放。
* **为什么把生成块显式化**：2048 的随机性只在生成块这一处。把它写下来，记录就与引擎的随机流
  解耦——**`undo` 因此只需要"把棋谱截到上一个 `move` 之前再重放"，不需要保存 RNG 状态**；
  编辑器造出来的局面与真打出来的棋也共用同一种记录。
* **被否定的替代方案**：① 命令行里用括号/逗号列表——无法在列表中间追加、无法单行报错，
  活棋局写不下去（这个写法在草案里出现过，被否掉）。② 把生成块留给引擎、记录里省略——
  记录就依赖种子与引擎实现，无法独立重放，第 3 条的全部收益消失。③ 用"是不是 2 的幂"
  的计算式校验——值空间是有限键集，计算式既不更强，扩大空间时还得改逻辑而不是加键。
  ④ 把 `set` 打在非空格上当作覆盖、而不是错误——那会让"记录是否被改过"无法判断，
  与本项目"数据要能自证"的立场相反。

## 替代方案

* **沿用训练样本记录当棋谱**：它记录的是每次决策的完整搜索上下文（含候选块），是训练数据
  的载体，但既不含"谁生成了哪个块"的显式序列、无法独立重放，体量与人可读性也不适合复盘。
* **JSON / JSONL**：机器友好，但手写与 diff 体验差，而且会诱导把分析结果等更多内容塞进去
  （首版明确不含），可读性这一条恰恰是选文本的理由。
* **完整 GTP 实现**：本格式的兼容目标是"GTP 风格"而非完整 GTP；`a1` 的行序与坐标含义都
  与围棋不同，不追求被围棋工具直接使用。

## 验证方式

* **编解码往返**：`parse → apply → render` 后与原文逐字节一致。
* **边界拒绝**：越界值（2^18、非 2 的幂、`0`、`1`）、`set` 打在非空格、`set null` 打在空格、
  非法 `move` 全部报错；且**语法错误与应用错误是两种不同的异常类型**（第 7 条的两层）。
* **与规则参考实现对照**：`apply` 出来的 `move` 结果与
  `python/src/r2048/reference/rules_reference.py` 逐条一致（复用既有的跨语言向量思路）。
* **版本闸门**：`record_format` / `rules_version` 不匹配时读取即失败。
* **端到端**：WebUI 编辑器摆出的局面导出为棋谱，再由复盘页载入并步进，与导出前逐格一致。
