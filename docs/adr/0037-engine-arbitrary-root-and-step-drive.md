# ADR 0037：引擎的任意局面与逐步驱动（会话模式）

- 状态：已采纳
- 日期：2026-10-08

## 背景

交互界面必须能回答两个**整局驱动回答不了**的问题：

1. **"这个盘面怎么样"** —— 从一个外部给定的局面起搜。此前做不到：`BatchedEngine` 的每一局
   都从 `opening_board(base_seed, episode)` 派生（`start_episode`），配置在构造时冻结。
2. **"AI 在这里会怎么走"** —— 搜索的中间态要有出口。此前根访问数只在整局结束时随 episode
   返回，逐方向的访问数/Q/先验没有任何读取入口。

另一条现成的路径也不够用：`RolloutMcts::search(const Board&, ...)` 确实能吃任意局面、也确实
返回 `visits`/`q_mean`，但它是**纯 C++、不含网络**，而且没有绑到 Python。

旧版当初走的是另一条路：不动批引擎，另建一个单盘面、只查询不落子的 `BoardSearch`，把预测缓存
与 PUCT 选择/回传提成共享原语，并要求重构后 `SearchEngine` 逐位不变
（`.reference/2048ai/docs/adr/0006`）。本版**没有跟随**，理由写在下面。

## 决策

在 `BatchedEngine` 上加一组**会话驱动**，不另建引擎：

1. `set_root(const Board&)`：把外部局面设为当前根（摆棋 / 载入棋谱 / undo 之后调用）——
   它就是 `start_episode` 里派生开局那一行的替代；同时重置搜索树、步号与累计得分。
2. `begin_analysis(uint32_t simulations)`：从**当前**根重开一次分析，预算 N 次模拟。
3. `report_root() -> RootReport`：读根局面的每方向 `visits / q_mean / one_ply / prior`、
   `root_value`、`best_action` 与 `legal_mask`。**这些数就是选招时读的同一批**——
   `finish_step` 写候选块与选方向都从 `root.edge_*` 取，所以面板上看到的与引擎走出来的
   不可能有两套口径。
4. `commit_step(int action)`：走一步并提交；`action < 0` 表示由引擎按 `decision_mode` 从当前根
   里选。**生成块由引擎自己生成并回报**（`spawn_index` / `spawn_exponent`）。
5. **不提交**：分析模式下 `pump_lane_range` 命中预算就停在报告处，不调 `finish_step`；
   分析模式下 `Advance::done` 的含义是"预算跑满"，与整局驱动的"目标局数达成"不是同一件事。
6. 为让"选择"与"提交"能被分别调用，把 `finish_step` 拆成 `select_action` + `apply_action`
   （行为不变：`finish_step = apply_action(select_action(lane))`）。**既有调用点一行没改。**
7. 会话模式要求 `lanes == 1` 且 `collect_samples == false`，违反即抛。
8. **会话里的终局 = 收工**：置 `finished` 并**清掉 `needs_new_episode`**。整局驱动里
   `needs_new_episode` 是"该换局了"的信号；会话里若留着它，下一次 `begin_analysis` 会让
   pump 去开一副随机开局——用户看到的是"自己的残局忽然变成了别的棋盘"。
9. **时间上限不在这里**：调用方在 `advance` 循环里看表，到点就停手读 `report_root()`。
   `RootReport::simulations` 如实反映实际完成的模拟数，所以"时间到了"不会被伪装成"预算跑满了"。

## 理由

* **为什么扩展而不另建**：本项目要的三件事在批引擎里都已经有现成机制——`finish_step` 本来就在算
  根的边统计（候选块就是这么写的），`reset_tree` 本来就是"每个决策步重建一棵树"。所以扩展面只有
  两点："根从哪来"与"停在报告处"，而不是把缓存与 PUCT 从热文件里抽出来。少一次大重构就少一次
  "逐位不变"的举证负担。
* **被否定的做法**：① **在 Python 侧跑一局再截取**（拿 `run_evaluation` 跑 1 局）——它从引擎
  派生的开局起跑，给不了给定盘面的答案；② **把生成块放进 Python**（旧版的选择：会话层用
  `ai2048.rules.spawn` 生成随机块并回报客户端）——那要求 Python 再实现一遍 90%/10% 与位置采样，
  与"规则只实现一次"（ADR 0004/0005）相反。现在生成块由引擎回报，Python 侧一行规则都没有。
* **一条新的定量事实（实测）**：分析预算 N 下，根各方向的访问数之和是 **N − 1**。恰好一条模拟
  用来求值**根本身**（它停在根上，一条边都没走过）。这与整局驱动同源，来自"根节点还没被求值时
  只允许一条在途模拟"那条保护（见 `pump_lane_range` 里的注释）。测试把它钉成
  `Σvisits + 1 == simulations`：**只丢一条、不多丢**——保护一旦失效，这条会立刻变红。

## 替代方案

* **另建 `BoardSearch`（旧版 ADR 0006 的路线）**：分离干净，分析页的需求是一等公民；但要在
  `batched_engine.cpp` 这个被跑谱与评测依赖着的热文件上做一次大重构（抽 `PredictionCache` 与
  PUCT 自由函数），并在本项目里多出第二套搜索驱动。旧版为此专门设了"重构后逐位不变"的回归门
  ——那是真实代价，不是形式主义。
* **给批引擎加"一次分析多个盘面"**：会话是"一个盘面、一步一步走"，多盘面并发会让"当前盘面"
  这个概念失去单数；而且多 lane 的批组成会改变逐局结果（ADR 0017），分析口径会更难说清。
* **把时间上限做进 C++**：需要引擎内部读墙钟并在搜索中途可中断，而"在哪停"没有天然边界
  （不像跑谱有"局与局之间"）。放在调用方更简单，代价只是"部分分析"要如实标注——而那本来就
  应该被标注。

## 验证方式

* **回归门（最重要）**：既有 7 条整局驱动用例**一字未改**且全部通过；`ctest` 六个套件全绿。
  这是"这条新路径不影响原来那条"的直接证据。
* 新增 5 条会话用例（`cpp/tests/test_engine.cpp`）：
  1. 任意根局面：请求里必须出现给定的那个盘面；`simulations == 预算`、`Σvisits + 1 == 预算`、
     合法掩码来自给定的盘面；
  2. 按指定动作提交：得分增量与 `apply_move` 一致，最终盘面与 afterstate **恰好差一格**，
     那一格等于回报的 `spawn_index`、值为 1 或 2（指数）；
  3. `commit_step(-1)` 选出的方向 == `report_root().best_action`（面板与引擎同口径）；
  4. 终局不开新局：终局局面回报 `terminal`，随后 `advance` 既无请求也无新对局；`set_root`
     之后可以恢复；
  5. 配置闸门：`lanes != 1` 或 `collect_samples` 必须被拒绝。
* **尚未验证**：真实网络权重下的分析结果（合成结果全 0 只验证协议与流，不验证搜索质量）；
  时间上限路径（在 Python 侧驱动，见会话协议那条 ADR）。
