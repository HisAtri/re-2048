# ADR 0038：会话进程与文本协议（三层结构）

- 状态：已采纳
- 日期：2026-10-08

## 背景

界面要能"看着一个盘面一步一步走"，而仓库里现有的驱动形态都是**跑整局**：`run_selfplay`
跑到目标样本数、`run_evaluation` 跑满目标局数，两者都不接受任意起点、也不汇报搜索中间态
（引擎那一侧已由 ADR 0037 补齐）。缺的是**会话**这一层：一个盘面 + 一条棋谱 + 一个引擎，
外部按命令推进。

还有一层更基本的问题：界面该跑在哪个进程、用什么跟引擎说话。旧版
（`.reference/2048ai` 的 ADR 0006）的答案是三层——引擎进程 ↔ 桥 ↔ 浏览器——并把它记了下来。
本版沿用这个形状，但**不重写桥**：Gradio 自带 HTTP/WebSocket，它本身就是桥。

## 决策

1. **三层**：会话进程（headless，stdio 文本协议）↔ Gradio 进程（协议客户端 + 组件 +
   作业监督）↔ 浏览器。Gradio 负责浏览器那一跳，所以旧版的 FastAPI 桥这次不需要存在。
2. **协议是 GTP 风格的文本**：一行命令，应答以空行结束；命令前可带数字 id，应答回显该 id。
   命令表：`protocol_version / name / version / list_commands / state / clear /
   set <值> <坐标> / move <方向> / genmove / undo / load / save / analyze /
   set_strategy / set_simulations / set_time_ms / quit`。
3. **`is_during_search` 帧**：`analyze` 先回一行 `=` 认领请求，随后每 ~150ms 一帧
   `info <json>`，最后以 `is_during_search: false` 的终帧与空行结束。调用方只等最后那一帧，
   但可以在搜索进行中就把访问数的增长画出来。
4. **状态变更命令一律回整份状态**，于是界面一次往返就拿到新盘面。
5. **命令词汇与棋谱是同一套**（`clear` / `set <值> <坐标>` / `move <方向>`）：`set` 的值域与
   坐标校验**直接复用 `records` 的解析器**，不会出现"能写进棋谱但不能通过协议摆"的两套规则。
6. **棋谱是会话里唯一的事实源**：盘面、得分、步数、合法方向都由重放棋谱算出。于是 `undo`
   只是"截断到上一个 `move` 之前再重放"——**不需要保存随机数状态**（这是 ADR 0036 把生成块
   显式化的直接回报），也不需要引擎提供"反走一步"。
7. **会话默认 CPU**：旧版实测 batch 只有 1~5 行时 CUDA 反而更慢（0.77ms vs 0.42ms），而且这样
   不会和跑谱/训练抢那张唯一的 GPU。
8. **`best_action` 与引擎同源**：报告里的"引擎会走哪一步"直接用引擎自己的选招
   （`RootReport::best_action` 调 `select_action`），所以面板显示的与真走的那一步不可能不一致；
   贪心档也因此有值（它没有访问数，选择来自 r+A 或先验）。
9. **会话不写数据批**：`collect_samples=0`、`lanes=1`，C++ 侧拒绝别的配置（ADR 0037）。
   `analyze` 的口径（批组成）与评测不同，这件事**跟着结果一起回给调用方**
   （`report.protocol`），因为批组成会改变结果（ADR 0017）。
10. **编辑与复盘不需要模型**：没给 `--checkpoint` 的会话照样能摆棋、载入、导出、undo，
    只有 `analyze` / `move` / `genmove` 会报一条说清楚原因的错误。棋盘编辑器与复盘页因此
    不依赖任何权重。

## 理由

* **为什么独立进程而不是让界面直接调库**：引擎会崩、模型要换，而界面不该跟着一起倒下；
  而"单一持有者"这条约束（引擎不支持并发独立搜索）在独立进程里是天然的，不需要在界面里
  再摆一把锁。代价只是一条协议。
* **为什么是文本而不是 JSON 帧**：它要能被人手敲着调——
  `python -m r2048 session` 之后直接敲 `set 2 a1` 就能用。JSON 帧会把这个能力换掉，
  而它在这里几乎不占成本（每局几百行）。
* **为什么回整份状态而不是"改了什么"**：界面需要的是"现在是什么样"。回增量会让前端必须
  自己维护一份盘面副本，而那正是"屏幕上的棋与记录的棋不一致"的来源。
* **被否定的做法**：① 界面直接 `import` 引擎并在 Gradio 回调线程里调它——Gradio 回调是
  多线程的，而引擎不是为并发独立搜索设计的（会出现两个搜索同时写一棵树）；② 旧版的 FastAPI
  桥——Gradio 自己就是桥，再套一层只多一层要维护的东西；③ 把 spawn 放进 Python 会话层
  （旧版的选择）——那要求 Python 再实现一遍生成块规则，与"规则只实现一次"（ADR 0004/0005）
  相反；现在生成块由引擎回报（ADR 0037），会话只把它写成一条 `set`。

## 替代方案

* **每次命令一个进程**（`r2048 session --command "set 2 a1"`，用完即走）：省掉协议与生命周期，
  但每次都要重新载入模型与 CUDA 上下文，交互完全不可用。
* **WebSocket/HTTP 直连引擎**：与"独立进程 + 文本协议"是同一个架构选择的两条实现路径；
  文本协议还能被脚本与人用，所以先取它，将来要换传输也不必改语义。
* **把会话状态放在前端（浏览器）**：刷新即丢、多标签页互相踩，而且规则会被搬进前端——
  与"选招与规则只有引擎一处"冲突。

## 验证方式

* `python/tests/test_session.py`（15 条）：
  1. **棋谱是唯一事实源**：编辑/落子/undo/载入之后，`盘面 == 重放(棋谱)`；应用不了的命令
     不进棋谱（长度不变、错误照样抛）；
  2. **`undo` 不需要随机状态**：走两步→退一步→盘面回到走第二步之前；没有可退的步时返回
     `False` 而不是抛异常；
  3. **分析与落子同源**：`play(None)` 走的正是 `analyze()` 报出来的 `best_action`（搜索档与
     两个贪心档都测）；生成块与 afterstate 恰好差一格，那格在 afterstate 里是空的，
     值是 2 或 4（指数 1/2）；
  4. **协议**：id 回显、`?` 报错、`set` 与棋谱共用键表（面值 2048 → 指数 11；越界值、
     非法坐标都被拒）、`analyze` 的流式帧数量与终帧标记、`analyze simulations=4 strategy=value`
     这类一次性覆盖；
  5. **真子进程冒烟**：管道驱动 `python -m r2048 session`，覆盖命令表、编辑、保存、
     没有模型时的报错、`quit` 之后退出码为 0。
* **实测记下的两条协议陷阱**（都是这次被测试逼出来的，不是设计时想到的）：
  ① 应答**必须**以空行结束——少了它，调用方"读到空行为止"就永远读不完，两条连续应答也会粘在一起；
  ② 客户端遇到 `?` 必须**先把这次应答读完再报错**，否则残留的结束空行会留在队列里，
  让下一条命令读到上一次的应答——错位之后每一条都对不上，而且看不出来。
* **尚未验证**：真实浏览器端的形状（在 WebUI 那一条 ADR 里）；多客户端同时接一个会话
  （现在按"单一持有者"设计，没有做并发接入）。
