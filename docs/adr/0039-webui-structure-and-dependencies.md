# ADR 0039：WebUI 的结构与依赖归属

- 状态：已采纳
- 日期：2026-10-08

## 背景

会话已经在独立进程里、有文本协议（ADR 0037/0038），缺的是界面本身：它放在哪里、依赖怎么算、
以及它跟引擎的关系。三条约束来自前面几条 ADR 与旧版的教训：

* 界面**不做棋规、不选招**——选招口径只有引擎一处（ADR 0006），界面上多一套判断就会分叉；
* 引擎不是为并发独立搜索设计的，而 Gradio 的回调是多线程的（ADR 0038）；
* 跑谱、训练、评测、推理这些核心流程**都不需要 Web 栈**，不该被一起拖进环境。

## 决策

1. **代码落在 `python/src/r2048/webui/` 子包**（`inventory.py` 清单层 + `app.py` 界面）。
   不另起仓库、不另起发行包：它要 import `session` / `session_io` / `records` / `paths`，
   分出去就得再维护一层版本与发布。
2. **依赖放在 `[dependency-groups].webui`**（`gradio>=5,<6`），**不进** `[project].dependencies`。
   装：`uv sync --group webui`；跑：`make webui` 或 `python -m r2048 webui`。
   旧版对 Web 桥也是这么处理的（它的 `server` 组），理由相同。
3. **三个标签页**：计算/分析、棋盘编辑器、复盘。**全部只跟会话进程说话**：界面拿到的是
   `state` / `step` / 分析帧的 JSON，它自己不碰引擎、不碰规则。
4. **自动执行是流式的，不是轮询**（订正，2026-10-09）：一开始用 `gr.Timer` 每 0.25s 打一次
   会话，实测是一屏 **50 req/s** 的请求洪水（浏览器 Network 里全是 `data?session_hash=...`），
   而且空盘面时它把"当前盘面是空的"这条错误每 250ms 刷一遍。现在改成**一个生成器事件**：
   一次调用里每走一步 yield 一帧，浏览器只维持一条长连接。节奏仍按 ADR 0037
   （`max(上次移动 + 间隔, 搜索完成)`）：一步做完之后才补睡"距上次移动还差多少"，
   所以搜索不会被砍断、间隔只限制最快速度。停止靠一个标志位，由「停止」按钮置位。
5. **棋盘是组件**：自带一份带 `r2048-` 前缀的 CSS（4×4 网格 + 行列坐标 + 标准 2048 配色 +
   生成块/选招标记）。此前用裸 `<table>` 加内联宽度，格子会被容器拉变形。
   **底色与字色必须成对地测**——只查"颜色出现过"是不够的：上一版把两者对调了，
   测试照样通过，而在浏览器里只是"看着丑"，不报错。
6. **开局走 C++ 的 `opening_board(seed, episode)`**（新绑的一个函数），不在 Python 里重写
   生成规则：界面上"开一局"与跑谱用的开局因此是**同一个函数**、同一分布、同一条随机流推导
   （ADR 0004/0005 的"规则只实现一次"）。开出来的两枚块照样写成显式的 `set` 进棋谱，
   所以开局这一步又把随机性固定进了文件：同 seed 必然同盘（ADR 0036 决策 3）。
7. **清单层只读扫描输出根**，界面里**不手输路径**：模型、数据批、棋谱都从下拉里选。
   模型扫描**按整个输出根递归 `*.pt`**，不写死 `runs/` 与 `models/` 这些子目录——
   模型的落点一直在长（训练 run 下、发布位、实验目录），写死子目录会让"新放出来的模型
   在下拉里看不见"，而看不见的原因完全不可见。元数据只读 pickle（`map_location="meta"`，
   权重留在磁盘上），实测 20 个 checkpoint 0.05s，所以全根扫描的代价可以忽略。
8. **下拉里每一行是"相对输出根的路径 + 训练目标"，`last.pt` 默认不列**（订正，2026-10-09）。
   全根扫描的第一版把标签写成了"父目录/文件名"，于是列表变成一列读不懂的
   `value/model.pt`、`policy-head/model.pt`——**同名 checkpoint 在每个 run 下都有**，
   而 run 名（真正能区分它们的那个词）恰好被丢掉了。改回相对路径之后 run 身份回来了，
   相邻行还共享前缀、读起来成组。另外 `last.pt` 是断点续跑的落点、每个 run 里都有一份，
   混进来让列表翻倍却几乎没人要选它，因此默认藏起来（要时用「含续跑点」勾上）。
   默认选中优先**完整模型**（`training_target` 是 dual/joint）：列表按路径排，
   第一个很可能是只训了一边的半模型，而默认值往往就是用户直接点的那一个。
   `model_id` 不进标签：它常是"数据批 + 配方"拼出来的长串，塞进去每行都撑爆。
9. **运行与停止是同一个位置上的两个状态**（订正，2026-10-09）：不是两个并存的按钮。
   点「自动执行」之后它变成「停止」，停下来再变回来（靠 `visible` 互换；不能只用一个按钮，
   因为 Gradio 会把同一控件的第二次点击排进队列，"停止"就点不动了）。自动执行期间手动控件
   置灰——不是靠"点了再说不行"，而是直接 `interactive=False`。
   与之配套：**"模式"这个单选项取消了**——它其实只是"自动执行在不在跑"，用一个开关就够。
10. **搜索参数在下一次分析或落子前应用**：每次动作前都把设置发给会话，所以没有"应用设置"这一步；
    按钮只负责建立/替换会话，叫「连接 / 重新连接」。参数常驻显示（后续修订见 ADR 0045），状态栏显示会话实际采用的策略与模拟数。
11. **状态收成一行 chip**：模型 · 设备 · 策略与模拟数 · 得分/步数/最大块 · 种子 · 能不能走。
    "我现在看着哪个模型、什么口径"必须一眼可见——它决定了屏幕上的数字是什么意思。
    空盘面与终局分开标色（见 ADR 0040 决策 4）。
12. **默认只绑 `127.0.0.1`**；`--share` 才对外。界面能驱动引擎跑搜索，不该默认暴露。
10. **编辑与复盘不需要模型**：没选 checkpoint 时那两页照常工作（ADR 0038 决策 10），
    只有分析/落子会给出一条说清原因的错误。
11. **复盘只喂 `set`，不喂 `move`**："以当前局面开新一局"送的是 `clear` + `set ...`。
    协议里的 `move` 会由引擎生成一个块，而棋谱里的 `move` 后面跟着的是显式的 `set`——
    把棋谱的 `move` 当协议命令发，每步会多生成一个块，盘面立刻就不是棋谱里那盘了。
13. **连接身份由模型与设备共同确定**：用户更改任一项后，界面标为待重新连接；重连会重建会话并清空当前局面，提示先保存需要保留的棋谱。设置参数在下一次分析或落子前发送，状态栏展示已应用的口径。
14. **研究信息始终可达但不抢主流程**：搜索参数常驻显示（后续修订见 ADR 0045）；完整方向表、局面归属说明与指标解释继续显示，走棋后不把上一步选招标到新棋盘。
15. **键盘方向键只在页面空闲焦点时控制棋盘**：输入框、下拉框、按钮及可编辑区域获得焦点时不拦截方向键，避免干扰参数输入和控件操作。
16. **移动端优先纵向排布**：窄屏时棋盘与分析纵向排列，分析表只在自身区域横向滚动；反馈区域使用 `role="status"` / `role="alert"` 供辅助技术播报。
17. **跨页发送后返回计算页**：编辑器发送与复盘导出成功后切换至计算页；复盘同时显示命令前缀与实际棋步数，因为命令数还包含 `clear` / `set`。
18. **计算页限制阅读宽度并分出操作层级**：桌面内容居中限宽，状态栏跨双栏显示；棋盘操作和分析结果各自成组，空分析区提供明确引导，避免宽屏下棋盘缩在角落、分析侧留出大片空白。窄屏下两组改为纵向排列。
19. **界面用自有设计系统覆盖 Gradio 默认皮肤**：暖色纸面、品牌条、会话卡与分栏工作台，而不是一排默认表单控件。棋盘、十字键和分析表仍是自绘组件（`r2048-*`），Gradio 只提供布局与事件。

## 理由

* **为什么界面完全不碰引擎**：Gradio 的回调是线程池里跑的，而"两个线程同时驱动一个搜索引擎"
  会让两棵树的推进互相踩（引擎只保证同一实例被串行使用）。把它放在独立进程 + 一条锁后面，
  这条约束就不再需要界面来记住。
* **为什么依赖是可选组**：`make env` 是每次进项目都要跑的动作，往里加一整套 Web 栈会让
  跑谱/训练的人多等几分钟、多背一堆版本冲突。可选组的代价只是一条 `--group webui`。
* **被否定的做法**：① 界面直接 `import r2048_core` 并用 Gradio 的线程驱动——见上；
  ② 单独一个仓库/包——为三个页面维护一套发布流程，收益不明；
  ③ 把模型路径做成文本框——机器生成的名字（时间戳批次号、run 目录）手输必错，
  而且会把"输出根长什么样"这件事搬到用户脑子里；
  ④ 用 canvas 自绘棋盘——坐标要能被读到（用户得对着棋谱文字数格子），HTML 里的文本标签
  天然可读可查，也让"哪个方向被引擎选中""哪一格是刚生成的块"这类标注好做；
  ⑤ 用 `gr.Timer` 做自动执行——见决策 4 的订正（50 req/s 的轮询洪水）；
  ⑥ 把"运行/停止"做成两个并存的按钮——同时存在两个互斥动作的按钮，用户永远要先读一遍
  才知道哪个是当前有效的。

## 替代方案

* **每个标签页一个独立 Gradio 应用/端口**：多一个端口就多一处要记，而三个页面共享同一个会话
  才是它的意义（编辑器摆的局面要能发到计算页）。
* **把会话状态放在浏览器里**：刷新即丢、多标签页互相踩（与 ADR 0038 的替代方案同一条）。

## 验证方式

* `python/tests/test_webui.py`：
  1. **渲染**：棋盘必须带 a..d / 1..4 坐标，显示的是**面值**（2048）而不是内部指数（11）；
     棋盘是**组件**（有 `r2048-*` 的类、标准配色、网格布局），且**底色与字色成对断言**；
     分析面板把"策略头先验"与"引擎选招"分开标，并且把"口径与评测不同"显式写出来；
     没有结果时显示"还没有分析结果"而不是报错；
  2. **清单**：模型按元数据列出、坏棋谱仍然出现在列表里（步数标 -1，不被静默丢掉）、
     输出根不存在时返回空列表而不是抛异常；
  3. **界面发出的命令流**（无浏览器）：在真会话上跑一遍新开一局 = `newgame seed=...`
     （恰好两枚块、同 seed 同盘）、分析 = `analyze`、落子 = `genmove`/`move <方向>`
     （断言引擎走的那一步与分析面板一致、生成块被写成显式 `set`）、存档 = `save`，
     再把棋谱读回来**逐前缀重放**（这正是不需要随机数状态的理由）；
  4. `build_app()` 真把 Blocks 搭起来（缺 gradio 时跳过，让 `make test` 在没装可选组时仍绿）。
  5. **交互回归**：会话仅在模型或设备变化时重建；空盘面和终局不能启动自动执行；分析结果标记对应局面；所有 Gradio 回调返回值与输出组件数量一致。
* `python/tests/test_session.py` 另有开局那几条：`new_game` 出的局面恰好两枚块且指数 ∈ {1,2}、
  同 seed 同盘、开局不是一步棋（`move_count == 0`）、开完能分析能落子能撤销回开局、
  不给种子时也要能被重放；协议那一侧覆盖 `newgame seed=123` 与 `newgame seed=abc`（报错）。
* **后续工作台改造与浏览器验证**：见 [ADR 0045](0045-webui-workspace-design.md)。
  已在 WSL / Gradio 5.50.0 与 Edge 中验证主要流程、响应式尺寸及程序化切页；
  辅助技术的实际语音播报尚未人工验证。
